# Picer 性能测量与实现边界

更新：2026-10-20；当前维护版为 v1.5.5/schema47。以下区分已实现机制、历史实测和仍需真实硬件评测的边界，不给未测硬件承诺延迟。

## 基准运行

在同一台机器、相同电源模式和空闲负载下运行：

```powershell
dotnet run --project tools/Picer.Benchmarks -c Release -- 1000 30
dotnet run --project tools/Picer.Benchmarks -c Release -- 100000 30
dotnet run --project tools/Picer.Benchmarks -c Release -- 1000000 30
```

第三个参数可指定数据卷，例如 `-- 100000 30 D:\bench-root`；工具只创建和清理其自己的 picer-benchmark-* 子目录。合成 SQLite 清单生成吞吐不代表真实媒体解码、模型推理或网络扫描吞吐。

搜索分别报告约 1% 选择性的查询和全库匹配压力查询，不把两者混成典型 p95。至少重复三次，记录每次结果和中位数、p50/p95/max、工作集、分配量与 GC。UI 另测首屏、持续滚动 60 秒的掉帧及峰值内存。

## 测量条件

记录日期、提交、Windows/.NET、CPU、GPU/显存、内存、存储、媒体数量、唯一内容数、引用数、参数和缓存状态。首次完整扫描、有效增量清单、变更目录增量和日志失效回退应分别测量。数据库/源文件/缓存所在磁盘分别记录；远端记录网络 RTT、模型排队和代理状态。

WebDAV 对照包括 0/100 ms RTT、HTTP 500、超时和无权限。测试目录须隔离，不能在真实图库上运行故障或清理实验。历史性能报告只适用于其记录的版本和机器。

## 当前扫描与查询优化

目录描述不再先生成完整任务清单。照片和视频各自按索引游标分页发现，默认页大小 128；视频摘要有效性在一页内批量查询，避免逐项 SQL。发现生产者和模型工作线程通过容量 8192 的有界异步队列解耦，队列满时自然背压；处理并发由用户选择 1～4，默认 2，照片和视频仍分别受信号量限制。每项先提交本地数据库，远程索引同步按 20 次写入、30 秒周期以及任务结束三种条件异步合并触发，不阻塞下一项模型分析。中断或同步失败保留已提交结果，重新开始会跳过有效描述。目录树仍后台构造，新增文件仍由独立索引任务发现。

持久扫描清单和 NTFS USN 水位减少重复枚举。首次、日志断档、不可信事件、非 NTFS 或网络盘回退完整核验；已知元信息和根可用性仍需检查，因此不承诺每次启动 O(1)。取消或不完整扫描不进行缺失对账。

本地视频哈希缓存最多 128 项，除卷、文件 ID、ChangeTime 和长度外，还须核验有效 NTFS 日志 ID 及同一打开句柄取得的逐文件 USN。仅靠 ChangeTime 在快速改写时不足以证明未变；无可信日志或签名时完整读取且不保留缓存。清除会失效内存、持久清单和在途发布，清除后的首次扫描可能变慢是预期行为。详见[实际失败及 USN 修复](VIDEO_HASH_USN_FIX_2026-10-09.md)。

主照片列表使用 keyset 和虚拟化；其他接口按其分页契约处理，不声称所有字典和列表均不全量读取。UI 共享连接任务串行调度，独立长查询使用独立连接。

## 模型并发和缓存

目录描述默认 2 路、最多 4 路；照片与视频发现可并行推进，工作线程从同一有界队列消费，并分别遵守照片/视频并发门限。收费云端仍按策略串行。并发增加不保证显卡满载或更快，需同时测预处理、传输、模型排队、显存峰值和失败率。

相同视频内容在同库内共享分析，摘要锁内复核有效结果。预算按在途请求预留、实际请求记账，缓存命中不能重复计费。视频帧写入独立生成目录并在成功后发布，海报按内容身份复用，保留仍被其他引用使用的旧代际。

## 同步与清理

服务镜像按变更水位分页，未变化时跳过媒体与元数据传输。重置必须完成稳定范围核对再清理所属镜像；取消和变动中的分页不触发全库删除。媒体数量相同不能代替变化检测。

手动清除先停止写入者再清缓存，等待时间应与任务取消延迟分开测量。末引用清除共享资产，非末引用只清理所属位置及独立副本；清除耗时不能作为“释放了原文件空间”的证据。

## 远程读图、视频与流式播放改造结论（2026-10-10）

五项改造已随 v1.3.5 发布并部署，实施、测试和发布证据见[远程媒体实施记录](MEDIA_STREAMING_IMPLEMENTATION_2026-10-10.md)。以下瓶颈描述针对 v1.2.1 旧链路，用于解释改造原因，不代表新二进制通道仍会整文件传输。此前一次资产请求约 38.6 秒，包含读文件、Base64/JSON 编码、发送锁等待和发送，不能单独认定磁盘慢。

旧链路瓶颈：照片缩略图缓存未命中时先传完整原图，再在服务端缩图；资产整文件编码成 Base64，并通过单个 WebSocket 的发送锁串行发送。GUI 原文件请求在返回 Stream 前也会完整缓冲 HTTP 响应，视频完整下载后才启动外部播放器。代理整文件接口还限制 64 MiB；服务端 Range 仅对已经收齐的 byte[] 生效，没有把 offset/length 传到源端。直接并发旧协议的多个 Range 会重复从代理取整文件，不能作为优化方案。新协议使用独立媒体连接，控制连接保持单一会话。

已实现的改造范围（实测结果与适用条件见实施记录）：

1. 源端生成并缓存缩略图与适中尺寸预览图，服务端合并同内容请求并缓存视频缩略图；保留 GUI 现有去重及有界并发。
2. 分别测量源读取、编码、排队、发送、服务端处理和 GUI 解码；日志仅包含请求标识、字节数和耗时，不记录原路径或媒体内容。
3. 建立端到端二进制流式分块传输，支持 offset/length、背压、取消传播和源文件身份校验；移除通过整文件内存上限限制大视频的做法，GUI 改用 ResponseHeadersRead。
4. **视频流式读取与播放**：短缓冲后开始播放，支持 HTTP Range 的 206/Content-Range、拖动跳转、邻近分块预取和缓存复用；不再等待全视频下载。优先采用原编码按需读取，不要求把所有视频转码成直播流。
5. 在不重复整文件传输的基础上，实测 2–4 路有界并发和独立媒体连接，小缩略图及控制消息优先；并发数不能突破源磁盘或上行带宽上限。

播放器可行性：VLC 提供网络流播放，mpv 支持网络缓存及 HTTP 请求；mpv 文档明确，HTTP 服务不支持 Range 时可能无法跳转。[VLC 官方说明](https://docs.videolan.me/vlc-user/desktop/3.0/en/basic/media.html)、[mpv 官方手册](https://mpv.io/manual/stable/)。不能据此保证每台电脑的任意默认播放器都支持网络 URL、当前编码或服务认证；直接用系统默认方式打开 HTTP URL 也不能保证会启动视频播放器。

Picer 已自行管理认证和固定公钥，通过只监听 loopback 的播放代理提供数据。外部播放器仅取得短期、仅限所选视频的本机播放能力，不向它暴露长期服务令牌；播放关闭后撤销并取消上游读取。本机代理校验随机访问路径、Host、来源及请求方法。自动模式识别 VLC/mpv 的程序名和产品信息；未知播放器默认下载，可由用户明确选择流式尝试，也可在播放窗口改为下载。GUI 安装包自带 Kestrel 运行库；播放器由用户安装和选择，不随包自动安装。

MP4 的 moov 索引可能在文件尾，Range 应允许播放器先读取尾部索引再按需读取视频。FFmpeg 的 faststart 可把索引移到开头，但不是所有文件都必须重封装；若兼容性要求创建 faststart、分片 MP4 或 HLS，只生成派生缓存，不修改原视频。[FFmpeg 官方格式文档](https://ffmpeg.org/ffmpeg-formats.html)。网络读取能力也不等于支持所有视频/音频编码，仍需播放器解码能力；当前没有自动转码、faststart、分片 MP4 或 HLS 回退；这些格式转换仅是后续可选设计，不属于现版本交付。

验收必须覆盖：大于 64 MiB 视频首帧不等待完整下载、前后拖动、尾部 moov、断网/重连、取消后源端及时停止、源文件改写时不混合分块、峰值内存有界、视频读取期间缩略图仍可响应，以及令牌不进入播放器命令行/日志。记录冷暖缓存的首帧时间、跳转延迟、有效吞吐、实际源端读取量与峰值内存，不预先承诺加速倍数。

## 当前实测与验收边界

后续七项优化已实现：缓存按键拆锁、2～4 路流式窗口预读、≤64 KiB 精确探测、租约媒体连接复用、源端描述照片预处理、视口缩略图优先和独立后台一致性调度。参数、兼容回退、后台边界及本次验证见[七项性能与后台维护改造](PERFORMANCE_FOLLOWUP_IMPLEMENTATION_2026-10-10.md)。以下 v1.3.5 数据保留其原版本身份。
