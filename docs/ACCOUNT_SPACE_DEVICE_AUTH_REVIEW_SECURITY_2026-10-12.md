# 账号、空间与设备授权设计：安全和隐私专项评审

日期：2026-10-12。审查对象：[主设计](ACCOUNT_SPACE_DEVICE_AUTH_SDD_2026-10-12.md) 0.9 初稿。性质：静态设计与当前代码对照评审，**不是实现验收、渗透测试或生产安全认证**。未读取运行凭据，未连接生产服务，未修改程序。

## 1. 阻断项与修订建议

本次未认定已有代码出现新增 P0 缺陷；以下 P1 是目标设计在实现前必须关闭的歧义。不能仅以“实现时注意”关闭。

| 编号 | 级别 | 章节 | 发现与风险 | 可执行修订及验证 |
| --- | --- | --- | --- | --- |
| SEC-01 | P1 | 4.3、6.1、7.1/7.2、8.1 | DeviceGrant 必须属于账号，但未明确未登录 B 的申请最终属于谁。Owner 批准他人设备时，若把批准者当接收账号，会使他人继承 Owner 身份；若任意填写账号，则可越权代理成员。 | 区分 approverAccountId 与 subjectAccountId。首版未登录文件配对只能给批准者自己的设备，UI 明示账号归属；给其他成员配对必须先完成接收者账号认证/邀请接受并绑定申请，Owner 只能批准权限上限。将 subjectAccountId 与 membership 版本纳入服务端 enrollment、签名载荷和兑换重验。测试 Owner 为 Viewer 批准后，B 仍只能作为 Viewer，不能取得 Owner 控制面会话。 |
| SEC-02 | P1 | 4.3、7.3 | 首次自签名信任允许用“申请校验码”替代指纹，但此前校验码仅定义为设备核对，未规定覆盖服务身份。核对申请公钥相同不能证明连接的服务可信。 | 首版明确短码仅核对设备申请，不能替代独立获得的 SPKI 指纹。自签名首次接入先经可信线下渠道建立服务 pin，再提交申请；或明确设计覆盖 serviceId、origin、TLS SPKI、recipientKey、requestId 的完整信任协议并独立评审，不能只增加模糊“核对码”提示。负例测试替换服务 SPKI 且保持设备公钥/短码不变，必须失败。 |
| SEC-03 | P1 | 6.3、7.2 | 短期加密响应重放包保证网络重试，但未明确撤权、角色降低、空间冻结后是否还能返还此前响应，可能让幂等缓存绕开最新授权或延续旧权限。 | 幂等命中也必须重验账号、成员、grant、enrollment、security/auth epoch 与有效权限；相关撤销原子标记不可重放并清除敏感响应包。已确认成功的设备不能被迟到失败重试误当孤立 grant 撤销；定义客户端确认/服务端首次成功使用凭据作为完成证据，以及孤立授权清理条件。测试消费成功后撤销、再用相同 attemptId 重试拒绝；已正常使用的 grant 不因迟到请求被删。 |
| SEC-04 | P1 | 6.1、10.3、11 | Viewer 被允许“问答检索”，但生成式问答可能消耗模型、发送敏感上下文，与只有 Editor/Owner 可执行 analysis.run 的矩阵边界不清。 | 将本地/服务端索引检索与模型生成分开：index.read/search.read 仅允许检索；生成回答单列 answer.run（或明确定义受 analysis.run 管辖），还需空间 AI 授权、模型路由和预算。Viewer 默认不能凭问答路由调用收费模型或外发图文。测试每个问答、embedding 和代理模型入口均有明确权限与预算。 |

## 2. 其他应纳入定稿的修订

| 编号 | 级别 | 章节 | 建议 |
| --- | --- | --- | --- |
| SEC-05 | P2 | 6.2/6.3 | 将 DPoP 的资源端与 token endpoint 规则分开：资源请求使用 `Authorization: DPoP`，proof 包含访问 token 的 `ath`；token endpoint 的刷新证明绑定设备 key，不把 refresh token 当 access token 计算 `ath`。网络重试保持业务 requestId/attemptId，但每次生成新的 proof/jti 并处理 nonce challenge。重放缓存拒绝同一 proof，不应误拒合法业务重试。 |
| SEC-06 | P2 | 5.1、7.1、11 | 明确受信任 HTTPS origin 归一化为 scheme/host/port，拒绝 userinfo、片段、HTTP 降级；不同用途的 issuer、API origin 和 JWKS 地址须由可信配置白名单绑定。配对文件不能新增任意网络取钥地址。OIDC 外部提供方的域名可以与 API 不同，但必须是事先批准的关系；不能把“完全相等”误用为所有 endpoint 同域要求。 |
| SEC-07 | P2 | 7.1 | 文件字段 `serviceId` 与验证说明中的 `serverId` 不一致，应统一 serviceId；外壳、JWS header、payload 均执行限长/重复键/允许字段与类型检查。只有签名验证后的字段才进入最终授权确认，验证前展示的地址要标明“尚未验证”。禁止把 `kid` 当路径或可访问 URL。 |
| SEC-08 | P2 | 6.2、7.3、8.1 | 已要求设备更换密钥重新批准，补充私钥丢失/DPAPI 损坏的用户路径：按新设备重新配对、撤销旧 grant，不回退明文存储；Agent Windows 服务身份与交互用户 DPAPI 范围必须明确隔离。服务端重放包保护密钥应有独立 keyId、轮换/清理，崩溃转储和诊断不能包含其解密内容。 |
| SEC-09 | P2 | 9.3、13.3 | 已考虑 tombstone 与不可变备份，建议明确备份清除记录的保存位置必须独立于可被还原的旧空间快照；恢复发布前先应用清除账本，无法取得当前账本时维持 Recovering。定稿不能把“删除业务库”写作“所有历史备份立即擦除”。 |

## 3. 代码对照与已覆盖优点

只读核对了 [ServiceSecurity](../server/Picer.IndexService/ServiceSecurity.cs)、[IndexServiceHost](../server/Picer.IndexService/IndexServiceHost.cs)、[IndexSyncClient](../src/Picer.Core/Gateway/IndexSyncClient.cs) 和 [MediaAgent](../src/Picer.MediaAgent/Program.cs) 的相关入口。

- 当前安全类确实生成随机 32 字节共用 token，存在 DPAPI 不可用的保存回退；当前 HTTP 入口比较同一 Bearer token。初稿没有把这认作多账号实现，基线表准确。
- IndexSyncClient 当前存在 expectedSpkiPin 为空即接受证书的路径。目标设计明确禁止托管/v2 延续该兼容回退，须在后续实现测试中覆盖，不能仅保留文字。
- Agent 现有路径入口可见绝对路径/根匹配；设计增加最终路径和 junction/reparse 检查是必要约束。此次并未全面验证现有所有路径的逃逸安全，不能据此声称已通过文件系统安全验收。
- 每空间数据库、跨空间缓存和连接池隔离、来源精确路由、角色交集、单设备撤权、恢复后凭据失效、原文件只读及离线副本无法强制收回的边界均已合理陈述。

## 4. 复核要求和结论

初审结论：**有条件通过设计方向，SEC-01～04 修订前不建议定稿或进入认证实现**。SEC-05～09 应在同轮文档中明确，避免协议互操作和运维实现分歧。复核只检查文档是否形成可执行约束；实际安全验收仍需后续实现后的双空间越权、并发重放、撤权竞态、恢复和路径逃逸测试。

外部协议事实以官方 [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html) 为依据：资源访问的 DPoP Authorization、访问令牌摘要与重放保护规则。已读取官方 RFC 文本；网页工具连接失败后改以只读 HTTPS 获取同一官方文本核对。其他问题属于本项目设计一致性推理，不借规范背书为已验证实现。

## 6. 跨专项修订后的终轮复核

2026-10-12，再次核对 0.95 在其他领域评审之后新增的安全相关条款：

- 第4节服务连接配置不含秘密，不把邀请链接的 issuer 当信任根；在线申请与批准文件分别计时，服务端控制期限，用户不能修改文件自行延长。账号归属和独立服务信任约束继续有效。
- 第5节自建必须创建本地 Owner；设备私钥不能替代近期人类认证。临时 bootstrap 仅回环监听，具有 socket peer、Host/Origin、CSRF nonce 与 bootstrap secret 检查，拒绝 DNS rebinding、公共反代和转发头伪造，成功后关闭并清秘密。HTTP 例外不扩展到正式登录、授权或数据 API。仅建议将页面 GET 与提交 POST 的允许范围写清，属于非阻断措辞完善。
- 成员邀请与设备授权分别建模；接收者独立登录且匹配预期可信身份，不能凭相同邮箱字符串合并账号或取得成员权限。
- 第9节严格 purge reset 优先于普通断网保留策略，立即停止旧远程镜像展示、检索、播放并清理缓存，解决了“不知道清除项仍展示旧库”的隐私风险；离线设备无法强制擦除的限制仍如实说明。
- 第12节控制面/RestoreGuard 的独立磁盘保留、撤销专用队列与失败时拒绝沿用授权缓存，避免容量耗尽时假报撤销成功。无法满足保留空间的部署不进入托管模式；实现必须注入磁盘满和排队饱和验证。

终轮结论：新增内容没有引入设计阻断，**维持安全与隐私专项同意定稿**。没有新增生产访问、运行凭据读取或程序实现修改；本报告不扩大为运行时安全认证。
