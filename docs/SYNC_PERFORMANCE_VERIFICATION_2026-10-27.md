# 索引同步性能修复与验证

## 问题与修复

旧实现对每条照片写入重新创建并编译 SQL。随着同步触发器增多，SQLite 编译成本明显上升，完整测试曾在十万条记录的初始化阶段触发十分钟无进展保护。现在复用照片插入、更新及镜像写入命令，每次绑定当前事务并清空、重绑参数；数据库关闭时释放命令。回滚后的下一次写入和跨批次镜像写入均有回归覆盖。

人工元数据分页中的相关子查询原来包含身份匹配 OR 条件，查询计划反复扫描同一发布者的身份映射。现拆分为两个独立 EXISTS 查询，使用已有的实体类型和目标 ID 索引；内容引用绑定仍保留，来源隔离条件不变。

没有新快照时，也执行有界派生日志压缩，避免用户停止编辑后旧日志长期不被清理。清理查询显式绑定当前事务，修复重复使用已结束事务的问题。

后续还为同步接收批次内相同 SQL 增加事务范围内的命令复用，以及镜像人脸与人物关联写入命令复用。后者同样在每次调用时重新绑定事务，保留模型版本隔离；回滚后继续写入、同模型缺失嵌入的保留及跨模型清空均有回归覆盖。其端到端收益尚未单独测量，不将下表照片写入数据套用到人脸写入。

## 实测证据

测量机器：Windows 10 专业版，Intel Core i3-4130 3.40 GHz、4 个逻辑处理器，约 16 GB 内存。构建、测试或迁移并行会明显争用资源，因此不同阶段的整机耗时不能直接当作单一代码改动的收益。

同一台 Windows 机器、同一份旧数据副本，分页查询返回的 501 行内容完全一致：原查询 10427.23 ms，优化后 7.59 ms。此数字仅表示该 SQL 查询，不代表整个同步流程或模型描述速度。

独立的 1000 条合成记录写入测量如下，单位为毫秒；不是生产端到端耗时承诺。

| 操作 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 本地插入 | 8704.24 | 504.22 |
| 本地更新 | 11735.79 | 913.35 |
| 镜像插入 | 19127.54 | 382.81 |
| 镜像幂等重放 | 20311.00 | 187.62 |

原始证据位于本地忽略目录 `artifacts/sync-verification-20261026/`：`metadata-page-query-comparison.json`、`write-baseline-1000.json`、`write-optimized-1000.json`。

- 命令复用和事务、镜像、场景、索引相关回归：50/50，通过记录 `prepared-write-transaction-schema89.trx`。
- 新增分页回归：2 万条身份映射、500 条编辑，验证分页与其他发布者隔离及查询耗时上限，1/1 通过，记录 `metadata-paging-performance-schema89.trx`。
- 2026-10-27 严格构建：零警告、零错误。
