# 训练应用原子性与来源回执

## 触发问题

远程 GUI 应用训练结果时，不能只修改本机镜像；服务端人物编号与来源电脑的编号也不能直接互换。原有替换流程还可能先清除旧原型，再因无效结果失败，留下缺少运行数据的状态。

## 本轮实现

- 远程应用和回滚通过照片空间服务提交。请求携带开始操作时的镜像 epoch 与活动工件版本；服务端校验后，在同一事务中更新原型、策略及工件状态。重复提交已应用工件可重试，旧镜像和竞争应用返回冲突。
- 来源工件使用来源身份映射解析人物编号。原始工件 JSON 保持原样，运行数据单独转换；模型版本不同的数据不会混用。
- 本地应用也采用单事务，结果包含无效人物、向量或阈值时回滚，保留原先的活动工件和运行数据。
- 来源电脑通过 `POST /api/sync/v2/training-applications` 分页取得本来源的活动工件应用回执。回执仅含工件身份、模型、应用时间、内容摘要及格式类型，不传输另一个来源的聚合数据。每页最多 100 项。
- 只有已完成全目录、照片、视频、人物授权发布的来源才请求回执。服务端复核设备、发布者、epoch 和全部目录绑定；部分目录授权不获得训练聚合状态。
- 来源收到回执后校验已有工件摘要，在同一事务中恢复运行数据和远程应用时间。尚未确认上传的本地应用保持不变，重放不产生新时间戳；本地已经清除的工件不会因旧回执重新出现。
- schema91 为工件、原型和策略记录已确认的来源状态指纹。服务端忽略来源未变化的旧快照，来源端只在本地应用状态与已确认基线一致时接受远程回执；不比较两台机器的墙钟时间来判定胜负。新的明确训练应用按服务端接收顺序生效，历史工件保留，不扩展为人物人工身份字段的冲突策略。
- 升级后的首次训练基线不把既有远程运行状态视为旧值：先保留权威状态并确认来源指纹，再回传应用回执。新增基线表只保存身份与摘要，不保存人物嵌入；基线和批次回执在同一事务中提交。
- GUI 推荐、候选分组及拆出人脸的失败显示在窗口状态栏，避免网络异常直接从异步命令逸出。拆出操作在等待前固定选中对象，避免等待期间选择变化导致操作对象变化。

## 空间与来源的归属边界

应用回执针对**来源上传的工件**。照片空间单独训练、混合多个来源的工件属于空间模型运行配置，不能借基本索引同步复制到每台来源电脑，否则会把其他来源的训练聚合数据带入本机。它们在空间中应用，产生的媒体分析结果、人物建议和用户决定仍按对应媒体来源同步。

本轮不会为没有唯一来源归属的空间模型猜测归属或伪造一个来源工件。若以后需要把空间混合模型分发到来源端，需要另行设计明确授权及工件投影；它不属于本次“一键索引巡检”自动修复的内容。不能把来源回执表述为所有空间模型工件均已下发。

## 验证状态

schema90 的训练原子性、来源回执、人物来源隔离和写入缓存专项共 7/7；真实账号服务 HTTPS 往返 1/1；随后训练模型边界和视觉专项 57/57、照片/视频人物来源隔离专项 67/67，均分别记录，不相加。schema91 新增了来源时钟超前至 2099 年、重复旧快照不得覆盖远程应用的回归场景，尚待验证。本报告不表示已经发布或部署。
