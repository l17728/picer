# 照片与视频描述结果同步一致性修复（2026-10-28）

## 问题与证据

用户报告目录任务显示“成功或复用 91、原有描述跳过 59”，但远程镜像照片分析表仅剩 58 条历史结果。成功计数在本地保存后递增；账号模式的 `PushMetadataAsync` 只上传人工元数据、人脸复核，未上传照片分析和视频摘要。远端快照对账会删除远端不存在的本地照片结果，视频摘要也受权威快照替换影响。兼容描述表的删除触发器还会删除内容派生缓存，因此不能把内容缓存视为可靠恢复来源。

这是结果持久化与同步协议的缺口；此前两个视频的模型 HTTP 传输异常、SQLite 写锁竞争是不同问题。模型 HTTP 200、运行内累计成功数，都不能代替持久结果与服务端确认。

## 修复

- 索引数据库 v92 增加 `description_versions`、按版本保存的 `description_outbox`、服务端 `description_receipts` 和一次性恢复标记，通过现有分阶段迁移及整库备份机制升级；不在运行中的旧 GUI 数据库上修改结构。v92 尚未部署，本轮直接完善该候选迁移。
- 远程账号模式将结果和待同步操作放在同一数据库事务中。照片文本索引复用该事务；视频内容变化时明确失败，不再静默返回并计为成功。
- 新增受照片空间 `index.write` 授权且限 GUI 设备的描述上传接口；核对空间 epoch、媒体 ID、大小、修改时间、可用内容哈希及结果结构。同一媒体的不同有效描述取并集，均保存在索引数据库中；按生成时间和稳定版本哈希选取当前显示结果，不因上传顺序丢弃旧版本。
- 服务端提交结果和操作回执后才返回确认；同操作 ID 重试幂等。确认丢失不需要再次调用模型。单项冲突不阻塞其他描述上传。
- 待同步和已确认但未在远端快照中出现的结果，都受快照保护；回读当前结果或版本集合包含对应版本后，才清理已确认操作。新协议中快照缺项不等于删除；明确清除媒体引用会清除其拥有的历史与队列，不复活已清除引用。旧协议不携带版本集合时保留兼容对账规则。身份或 epoch 变化时不将旧结果套用到新内容。
- 启动时为旧版本仍存留的本地照片描述、视频摘要补建待同步记录；已有操作 ID 保留。后台同步负责重试。
- 目录窗口另显示当前照片空间待上传数、服务端确认后待回读核对数，明确“成功或复用”是本机处理计数，不代表全部已同步。
- 本地重新分析失败也保留先前完成的版本。服务端视频摘要补齐更新时间；照片描述投影与搜索文本在同一事务更新，避免界面和检索内容不一致。

## 现场保护与恢复

遵守用户要求，现有 GUI、模型服务和索引服务未停止、未替换。E 盘只读留存程序定期读取已完成结果，独立保存到 `E:\picer-description-sync-20261028\captured-results.jsonl`，不会修改运行中数据库。截至首次清点，留存 21 条视频摘要；当天照片全文搜索文档查询为 0。该数量不是完整任务成功数，也不保证已消失结果全部可恢复。

`tools/Picer.DescriptionRecovery` 提供 `--dry-run` 和 `--apply`，使用数据库、留存文件、预期镜像 epoch 作为参数。检查媒体大小和修改时间、摘要与 JSON 的一致性；保留同一视频的全部不同完整版本，应用时再次检查身份，写入版本历史与待同步记录，再按统一规则选择当前结果。它不调用模型、不读取或修改原始媒体。另提供 `--audit <本地库> <设备凭据文件> <输出目录>`，使用现有设备认证及固定证书，读取服务端稳定快照和本地只读事务；凭据不写入报告。数据库升级及实际应用需在允许切换版本后进行；不能把只读演练称为已经恢复或已经完成服务端同步。

最近一次只读恢复演练读取 27 个留存版本，去重后对应 21 个视频，21 项符合回写条件、0 项被拒绝、模型调用 0 次。留存程序仍在运行，后续数量可能增长。两次在线 SQLite 副本获取分别达到 90 秒、120 秒时限，未形成可用于迁移的完整副本；未在这些不完整文件上执行恢复，也未对原库执行 `--apply`。实际回写必须在允许切换后取得关闭写入者的完整备份再进行。
