# 人脸人工状态的因果同步

2026-10-23，开发验证中，未发布部署。

现有“忽略/恢复”审核日志会同步显式 active/ignored 状态，但人物归属快照仍按 updated_utc 合并。“移回待分类”删除本机归属后，旧端重新上传 confirmed 归属时，单独的 active 审核状态不足以表达“已撤回归属”。新增回归按实际接收次序重放旧归属、审核日志及人工字段，分别验证忽略和移回待分类。`face-withdrawal-reproduction-schema68.trx` 1 项通过、1 项失败：忽略对照通过，移回待分类后出现 1 条不应恢复的归属。此结果确认真实缺陷，不能当作已修复。

schema69 / 协议 5 已接入人工状态字段、来源/人物身份翻译、范围过滤、分页、通知、迁移与冲突显示，初轮严格构建零警告、零错误，`face-state-initial-schema69.trx` 79/79 通过，包含原先失败的撤回归属场景。追加的身份映射、授权范围变化、迁移和永久清除验收仍在运行，不将初轮结果当作全部验收。人物合并同时补记被移动的已确认归属、被继承的描述与别名；目录实体删除和拒绝关系的完整协议仍不在本次完成范围内。

实现目标是把确认归属、忽略和移回待分类作为同一人脸人工状态字段，绑定人脸模型版本，复用服务端单调版本、基线冲突及幂等回执。机器建议不冒充人工决定；旧快照不能覆盖已有人工状态。人物 ID 上下行分别通过 publisher 的稳定身份映射转换，未授权人物范围不传输。显式撤回作为状态事件保留，不能仅靠归属行缺失推断。

已接入并继续验收的具体约束：

- `face-state / face ID / state` 保存 confirmed、ignored、unassigned 三态；载荷包含人物 ID（仅 confirmed）、人脸模型版本。人工入口与状态事件同事务提交。
- 复用 `PeopleService.InsertCorrection` 覆盖确认、移动、忽略、移回待分类等动作；人物合并的批量 SQL 需单独处理，不能遗漏。
- 旧归属/审核快照不能覆盖已有同模型人工字段；忽略删除归属与候选，移回待分类撤回确认归属但不把之后的机器候选当作人工确认。
- 源端上下行、授权范围过滤、身份认领、分页查询、冲突通知及操作回执均加入 face 身份；确认状态中的人物 ID 必须双向映射。不同来源及关闭人物授权的来源不得接收这些字段。
- 冲突 UI 显示人物名称及中文状态，不把 JSON 或服务端整数 ID 交给用户判断。名称只用于授权 UI 展示，不进入日志。
- 人脸永久清除同步清理该字段、冲突与回执；历史人工确认、忽略及明确撤回保守迁移。不得把自动 suggested 结果迁移为人工决定。

本记录尚不代表照片/视频所有人物元数据均已覆盖。视频内容共享时的来源归属隔离、人物拒绝、合并及目录实体删除等边界须逐项验证；整体剩余范围仍以 DEVELOPMENT_PLAN.md 为准。
