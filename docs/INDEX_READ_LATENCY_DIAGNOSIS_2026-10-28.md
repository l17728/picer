# 索引读取与视频详情分段耗时诊断（2026-10-28）

## 结论与范围

分钟级卡顿的主要原因已定位到 GUI 的全局数据库任务队列：后台人脸全量同步在同一个任务锁中执行几分钟，用户读取本地镜像也必须等待。关键帧已缓存时仍会先进入第二次数据库任务，因而再次排队。不是把 163 秒全部花在 IndexService 网络请求上。

独立 HTTP 测量也发现秒级服务/转发等待以及全量元数据传输开销。当前服务没有 `Server-Timing`，因此客户端响应头等待不能进一步准确拆成服务器鉴权、SQL、转发队列和网络往返；不能据此断言全是服务器 SQL 或网络带宽问题。

全程保持原 GUI、IndexService 和 MediaAgent 运行，不升级、不发布、不改写现场索引或原文件。新增可重复的只读探针，实际观测的是运行中的旧版本；前一轮描述全集修复候选尚未切换。

## 后台占锁耗时

18:30 以后的日志样本：

当前元数据包含 21336 条照片人脸、10442 条复核状态、1277 条候选成员。GUI 在元数据版本变化后读取全量集合；`UpsertMirroredFaces` 对所有人脸执行 UPSERT，没有跳过相同值；`ReplaceMirroredFaceWorkflow` 先删除再重建这些派生集合。它们在单个 `UiWork.RunDatabaseAsync` 中执行。已有内容派生、修订等触发器会增加写入成本；未做关闭触发器的对照实验，不能量化每个触发器的占比。

代码位置：

- `src/Picer.App/Infrastructure/UiWork.cs`：所有数据库任务共用静态 `SemaphoreSlim(1,1)`，读任务同样排队。
- `src/Picer.App/ViewModels/VideoViewModel.cs` 的 `LoadSelectedVideoAsync`：先排队读取转写、人物、摘要、关键帧和人物列表。
- 同文件 `MaterializeRemoteFramesAsync`：检查关键帧缓存之前，又通过 `UiWork` 执行 `Videos.GetAll().FirstOrDefault(...)`，只为取得一个视频而读取全部 529 条记录。
- `src/Picer.App/AppServices.cs`：`RemoteMirror.Faces`、`FaceWorkflow`、`ManualEdits` 分别作为较大的数据库任务执行。
- `src/Picer.Core/Data/PicerDatabase.cs`：`UpsertMirroredFaces` 与 `ReplaceMirroredFaceWorkflow` 的全量写入实现。

因此同一公共队列上的人物页面、照片详情、其他索引读取也可能一起变慢，不能只优化视频 HTTP 下载。

## 独立只读 SQL 与网络测量

使用同一现场库的只读连接，绕过 GUI 的任务队列但不改变数据库。每项读取三次，保持现场后台负载，不清系统缓存。

| 本地查询 | 实测范围 |
| --- | ---: |
| 单条视频 | 0.19–9.22 毫秒 |
| 全部 529 条视频 | 9.65–46.76 毫秒 |
| 转写、摘要、关键帧元数据各自 | 0.12–0.42 毫秒 |
| 人物时间线（含实际有 6 条人脸的视频 515） | 0.04–0.58 毫秒 |
| 8 人列表及关联数量统计 | 130–215 毫秒 |

这些是独立连接上的 SQL/行读取时间，不包含 GUI 队列等待、WPF 渲染，也不能等同于全部 UI 加载时间。

| --- | ---: |
| DNS，3 次 | 85–146 毫秒 |
| TCP 建连，3 次 | 22–103 毫秒 |
| 独立 TLS 握手，3 次 | 594–1247 毫秒 |

响应头时长包括客户端设备鉴权、服务端及代理处理、连接和网络等待；不能与独立建连/TLS 测量简单相加。正文读取可能包含服务端继续生产数据与解压，不能直接当作链路的理论带宽。全部 HTTP 样本返回 200，未触发本探针重试。

关键帧接口沿用 `AgentConnectionRegistry.RequestAsync` 的资产请求：服务端取得源端 Agent 返回的完整资产后才向 GUI 返回。源端日志中对应的六次 96315/54169 字节资产读取与发送耗时分别为 313、167、18、72、181、110 毫秒。该计时不包含请求到达 Agent 之前的转发等待，以及数据到达服务端后的处理。说明 3–17 秒的响应头等待并非主要花在源端文件读取；尚需服务端按请求 ID 的阶段计时才能精确区分其余部分。

## 优先处理顺序

1. 交互读取采用独立只读连接和一致性快照，写操作仍串行；不要简单删除写锁而重新引入 SQLite Error 5。缩短后台写事务占用的队列时间。
2. 人脸和复核集合增量对账，跳过未变化行，避免每轮整批 UPSERT/清空重建；不能把半更新的复核状态暴露给界面。
3. 关键帧加载复用本次选中视频的快照，避免缓存检查前再次全表读取和排队。保留媒体身份验证与取消规则。
4. 追加服务端鉴权、打开数据库、来源路由、Agent 等待、回传的分段计时，优化未缓存关键帧的转发链路；减少整库元数据响应。单纯调整 HTTP 超时或增加下载并发不能解决已证实的公共队列阻塞。

本轮完成定位和测量，尚未实施这些性能改动，也未重启程序。
