# 账号与空间授权 SDD：数据架构与同步专项评审

日期：2026-10-12。评审对象：[设计初稿](ACCOUNT_SPACE_DEVICE_AUTH_SDD_2026-10-12.md) 0.9，第 8～13 节为主。角色：架构、SQLite 迁移与同步一致性专项。方法：静态阅读设计及现有源码；未连接生产服务、未读取凭据、未执行迁移。本报告不代表功能实现或运行验收。

## 结论

每空间独立库、全局身份、按来源路由、恢复提升代际的方向合理。初稿尚有 2 项 P0、4 项 P1 设计缺口，建议补齐后定稿；不能把这些问题留给各模块自行解释。P0 指可能导致清除复活或持久化数据丢失，P1 指协议或迁移完整性不足。

## D01 · P0 · 清除后的恢复依据和“零标记”默认策略不闭合

位置：9.3、13.3、T09/T11。

初稿允许保留 tombstone，并把完全不留标记作为“若用户要求”的支线；本会话用户已经明确手动删除不保留任何索引等信息，不能再把用户既有要求推迟到以后选择。另一方面，内容库备份可能早于清除，控制库也可能恢复到旧版本；只说“清除记录参与恢复”没有指定清除记录的独立存储与耐久边界。把 dataEpoch 提升只会拒绝旧写入，不能识别旧备份里哪些媒体曾被清除。

修订建议：明确本项目默认采用严格清除策略；若保留最小同步墓碑，必须明确它不包含媒体信息且需要产品需求另行接受，不能视为已经获得授权。严格策略清除要轮换空间数据代际、关闭旧发布者写入，重新建立基线并清空旧 outbox 的自动提交资格。恢复必须有独立于恢复目标的删除屏障/清除账本，或把清除前备份标记为不可上线恢复；没有可信清除历史时默认拒绝旧备份发布。不得用“备份不可变”解释允许已删内容重新上线。若选择无实体标记，须明确以备份代际作整体恢复屏障，代价是不能从清除前备份直接恢复整库。

验收：清除后分别恢复旧空间库、旧控制库及两者，旧媒体均不得重新可见；全部清除历史丢失时恢复失败关闭访问，而不是继续提供服务。

## D02 · P0 · 本地 outbox 与服务确认的事务边界未定义

位置：4.1、9.1、9.2。

“批准后后台建立同步快照和增量 outbox”没有说明启动捕获与快照切点关系。若先快照再开启捕获，中间修改会丢失。初稿也未明确实体变更、operationId 去重、publisherSeq 和 changeSeq 在同一空间库事务提交。现有 [IndexSyncClient](../src/Picer.Core/Gateway/IndexSyncClient.cs) 的增量实际上比较全库指纹后推送，不能直接承担 v2 事务性 outbox 保证。

修订建议：本地业务变更与 outbox 同事务；先启用捕获，再取得一致快照与 cut。服务端实体变更、幂等结果、连续发布水位及变更日志同一空间库事务；发送确认发生在提交后。冲突和永久拒绝也要明确是否消耗序号：建议记录终态结果并推进连续已处理水位，可重试错误不推进；后续依赖失败实体的操作返回 dependency_failed。拒绝相同 operationId 不同载荷，采用规范化载荷摘要作幂等一致性检查。

验收：在每个持久化及回包边界模拟崩溃/丢包、首轮快照期间并发人工编辑和清除，无丢失、无重复效果、无永久堵塞队列。

## D03 · P1 · snapshotId/cutSeq 不足以保证分页快照一致

位置：9.1、12、T02。

有 snapshotId 和 cutSeq，但未定义切点对应的实体值如何保留。现有 [镜像增量实现](../src/Picer.Core/Data/PicerDatabase.MirrorChanges.cs) 根据变更 ID 读取当前实体；不能在 v2 中直接声称这就是历史切点的实体快照。长时间 SQLite 读事务又可能造成 WAL 持续增长。

修订建议：首版使用短时一致数据库快照生成独立只读快照文件，或等价的版本化快照；按 snapshotId 分页，不能每页重新查询可变主库。规定 TTL、磁盘配额、快照并发和取消清理，过期返回 reset_required。change 日志保留须覆盖活跃快照 cutSeq，超界明确重置。镜像在暂存库组装完整实体及关联，原子发布完成标记后才移除旧镜像；镜像单页数据和 checkpoint 同事务提交。失败保留旧可读库，不能把半截快照当作权威删除依据。

验收：分页间更新、删除同一实体及其人物关联；读取结果对应同一切点，后续增量恰好收敛；过期及磁盘不足不清空已有镜像。

## D04 · P1 · 控制库跨空间库授权栅栏缺少提交协议

位置：8.1、10.1、13.3。

初稿正确说明没有跨 SQLite 事务，但只具体描述建库/删库。来源转移、撤权、恢复 epoch 与正在写入的空间事务仍可能在“验证授权”之后、提交之前交错。仅给任务附加 epoch 并不能阻止旧任务在恢复新库后提交。

修订建议：增加每空间持久化 fenceVersion/写入租约。正常操作取得授权快照和空间写入许可，提交时在空间库内 CAS fence；撤权/来源迁移/恢复先在控制面进入封锁状态，阻止新许可，排空或取消旧写入，再在空间库落新 fence，最后发布 Active。每一步有 operationId、期望代际和可恢复 journal；崩溃后仍保持封锁，不按“控制面 Active”单独开放。明确旧 HTTP、模型结果、后台检查和媒体任务均经过同一入口。网络和模型等待不能占据这个写许可。

验收：来源转移和恢复各步骤断电；旧任务故意延迟到新 fence 之后回包，不得改变新空间状态。

## D05 · P1 · 克隆 LibraryId 与同内容 GlobalId 的冲突收敛未落到协议

位置：8.2、9.1、13.1。

`(LibraryId, EntityKind, LocalId)` 映射不能只依靠用户选择“作为新来源”来解决库克隆；如果新来源仍保留旧 LibraryId，相同 LocalId 会继续命中原 GlobalId。两台电脑首次发布同一 SHA256 时，各自 contentId 与服务端唯一内容记录的关联也未定义。

修订建议：新来源克隆生成新的 library incarnation 并重建映射、publisherId/outbox 序号，不复制凭据；迁移同一来源则采用显式交接，冻结旧 publisher、提升 routeEpoch，接续经确认水位。服务端唯一内容键冲突返回 canonicalContentId 和别名映射，引用归属不合并；后续关联统一解析别名。本地新实体身份由客户端预分配随机 GlobalId 或服务端返回映射，两种方式须选定一种，不依赖暂未拿到服务 ID 的线下实体关系。

验收：整库复制到 B、A/B 同时在线，及两个来源并发首次提交同一内容；人物/标签/视频派生关系不串位，共享内容只保留一份，引用各自存在。

## D06 · P1 · schema 迁移需增加新旧可执行程序的最小版本门禁

位置：13.1、13.2、M6。

初稿规定不能回退，但没有规定旧二进制如何被阻止打开新库。现有 schema 45 的连续迁移链和 [DatabaseMigrationSafety](../src/Picer.Core/Data/DatabaseMigrationSafety.cs) 能保障暂存迁移，不等于提供 v2 新库防旧程序写入机制。用户可能启动另一个目录的旧 GUI/Agent。

修订建议：客户端使用独立 v2 数据目录与受控切换指针，保留旧库只读备份；新旧程序不能共享活动路径。增加存储格式/最小 reader-writer 版本检查，新程序遇到更高版本拒绝打开。旧服务实例只能访问独立只读副本；安装器和启动协调在切换期间停用旧自动启动项并验证所有维护位置。迁移 journal 记录旧库到新空间/库映射与校验清单，任何步骤失败恢复指针而非改低 user_version。

验收：升级后启动保留的 v1.4.0 程序，不能写入 v2 活动库；迁移途中崩溃及升级撤回仍可找到正确的旧只读备份和新数据。

## 已确认的正向设计

- 每空间独立 FTS、向量、缓存、后台检查和来源路由，明确不只改认证中间件。
- 控制库不存媒体路径；来源端校验根、reparse point 和卷身份。
- 最后引用才清共享内容，缺失与离线不触发 purge；保留原媒体只读约束。
- 人工分类/不分类是版本化人工决策，避免重检测覆盖。
- 既有 [Agent 注册表](../server/Picer.IndexService/AgentConnectionRegistry.cs) 的无 agentId 任取代理逻辑已在设计中明确禁止。
