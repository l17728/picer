## 后续授权修复状态

用户随后要求修复所有未关闭审查项。以下保留初始发现证据；当前状态以本节及主审统一验证报告为准。

PERF-01～08 的汇总状态与验证证据见 [审查修复记录](SYSTEM_REVIEW_FIXES_2026-10-09.md)。PERF-03 已移除数量捷径；PERF-04/05 已改为子树 SQL、批量状态、取消预览、父目录去重与树控件懒加载。共享连接调用按已识别入口治理，照片内容锁改为固定数量分片，不随唯一内容数增长。以下“建议/问题”是初审证据，不是重复新增待办。

- PERF-02 已实现：每页只按该页路径批量查照片/视频；每扫描首次建立轻量缺失候选；源路径校验使用 GetSource 单行查询。路径查询使用 source_id 和 NOCASE 路径组合索引（由数据库专项迁移提供）。重复首分页不覆盖初始候选，乱序按不完整扫描保守处理。
- PERF-06 已实现：每个调用者仅取消自己对共享下载的等待；缓存提供独立下载 token、2 分钟期限与最多 8 路下载；下载结束按任务身份清理，避免旧等待者移除新代任务。UI 必须使用接收 downloadToken 的工厂重载，不捕获卡片 token。
- PERF-07 已实现：每内容可回收互斥锁、最多 4 路不同内容下载、异步可取消 SHA-256、单文件流式容量限制；LRU 清单初始化一次，后续按内存索引每批最多 64 个候选淘汰并让出；清理缓存递增代号，在途下载不能恢复清理前内容或淘汰新代缓存。
- PERF-08 及任务日志存储已实现：响应先流式转发给调用者，再尽力留存二进制 `.body`，旁边仅存小 JSON 元信息。单结果 64 MiB、总留存 512 MiB、7 天 TTL、最多 2000 项、4 路执行；超并发返回 429，结果超额/落盘故障不会把实时成功响应改成失败，最新任务状态保留 `result_storage_*` 原因，回放返回不可用。GetResult 文件流、Retry ResponseHeadersRead 流式转发，不再整块复制及 base64 序列化。
- TaskJournal 最新状态改独立 `service-tasks.sqlite`，查询不遍历 JSONL；启动流式导入旧日志并在事务提交后截断旧 JSONL，启动仅将最新的未完成状态标 abandoned。任务最新状态保留 30 天、最多 10 万项。原 JSONL 的逐事件历史不再继续累积。旧式 `.result.json` 受留存配额/TTL 清理，但不在内存解码迁移成新回放；原请求文件仍可用于失败任务重试。
- 媒体 purge 核查：当前只有照片 `purge-missing` HTTP/Pipe 入口，没有视频 purge API；此任务回放存储仅接受 video-probe/audio/keyframes/transcribe/people，因此照片 purge 不存在同照片 ID 的回放文件需清理。未来若新增视频 purge，必须同时清理关联回放及任务状态。
- 新增 DirectoryScanPagingTests 3 项、RemoteCacheConcurrencyTests 5 项；尚未在本专项自行构建，最终执行结果由主审统一记录。
- 新增 ServiceTaskStorageTests 6 项，覆盖提前流式输出、二进制回放、单结果配额、落盘失败、总量/数量上限、TTL、旧日志导入及重启最终状态；原 ServiceRetryRecoveryTests 同属必跑验证。

## 已实现：减少重复目录文件枚举

- `src/Picer.Core/Indexing/DirectoryMediaChangeTracker.cs`：进程内目录列表缓存，最多 4 个根；文件系统监控标记脏目录，每次仍检查已知目录修改时间，补偿事件尚未投递的常见窗口。只对新增或变化目录重新枚举文件与子目录。
- 后续增加持久 NTFS USN 清单：连续可信日志支持跨重启复用，失去日志可靠性、首次使用、监控异常/溢出、显式失效、强制扫描回退完整枚举及内容校验。没有持久日志支持时保留默认 10 分钟完整校验期限。闲置根由定时器释放，根淘汰和进程退出释放 watcher；扫描取消不发布不完整缓存。
- 监控水位在一次枚举中变化时，不将该轮标为完整枚举，避免该轮被用来推断未见记录已丢失。正常可读条目仍能处理。
- `DirectoryMediaScanner` 使用共享 tracker，原分页接口兼容；新增可选 tracker 参数供隔离测试。旧视频无 SHA-256 时重新读取，之后与照片相同地复用有效内容签名，配合另一专项的视频移动修复。
- `src/Picer.MediaAgent/Program.cs` 的目录扫描入口改为 `Task.Run`，首次大量同步文件枚举不再阻塞接收循环到第一个异步文件读取才让出；因此可以接收取消消息。WPF 本地入口原本已有 `Task.Run`，没有重复修改。

边界：跨重启优化依赖 NTFS 日志可读且水位连续；其他场景安全回退。仍检查目录时间和已知文件元数据，不能称为 O(变更文件数) 的完整扫描。持久待校验路径和已确认 SHA 防止未提交导入跨重启后被旧签名跳过；手动 purge 同时清理清单并使旧进程延迟保存失效。详见 [持久扫描实现](PERSISTENT_DIRECTORY_SCAN_IMPLEMENTATION_2026-10-09.md)。没有声称在网络文件系统或 2 GB 显卡设备上验收。

新增测试 `DirectoryMediaChangeTrackerTests` 覆盖未变化复用、强制/失效回退、新增/改名/删除子树、取消不提交、过期/新实例完整扫描、旧视频 SHA 补齐与复用。最终构建和执行结果由主审统一记录；本专项不把仅添加测试写作“已通过”。

主审收尾验证已通过：完整单元464/464、最终相关定向111/111及关键帧并发1/1、完整WPF69/69；严格构建零警告零错误。目录复用测试允许最多3秒等待系统通知稳定，仍要求最终完整状态且不重新枚举，生产监控水位规则未放宽。具体测试范围见 [总报告](SYSTEM_REVIEW_2026-10-09.md)。以下性能规模风险未用真实图库压力测试替代论证。

## 确认的问题与待补工作

### PERF-01 / P1：照片上传分页实际重复发送全源集合

发现位置：`src/Picer.Core/Gateway/IndexSyncClient.cs:86-94`，`PushImagesAsync` 对 `images.Chunk(200)` 遍历，但原 POST 匿名对象使用 `images` 而非 `images = batch`。例如 10,000 张将原集合发送 50 次，而进度仍看似每次只增加 200。造成传输、序列化和服务导入工作约 50 倍放大，并可能触发请求体上限。

本轮已转交健壮性专项修复与 HTTP handler 回归，勿重复实施。验收：201/401 条记录每次 <=200，所有 ID 恰好发送一次，取消不发送后续页；执行结果见统一报告。

### PERF-02 / P1：扫描每一页重新物化整个源，整体趋于平方复杂度

位置：`src/Picer.Core/Indexing/DirectoryMediaImport.cs:60-62`。每次 `ApplyCore` 均 `GetImages(sourceId, includeMissing:true)`、`VideoRepository.GetAll()` 后构造字典，再处理最多 100 个复用项或最多 5 个深读项。10 万条初始深扫可能反复物化全源约 2 万次。新增文件系统缓存并不解决这个数据库阶段。

建议：首次页构造缺失核对所需轻量候选快照；每页仅按页中路径批量查对应记录；视频查询应带 source_id 条件；最终缺失核对保持快照签名校验。不要把数据库连接或长事务保留跨网络分页。

验收：隔离 1k/10k/100k 数据库，用 SQL 执行计数和物化行数比较相同页大小的总工作量；分页重放、乱序、取消和中途变化不误标 missing。严重性来自确定的算法放大，尚未给出实机吞吐数字。

### PERF-03 / P1：镜像用“数量相等”判断照片未变化

位置：`src/Picer.App/AppServices.cs:368`，`mediaComplete = !fullMediaReconciliation && localSource.ImageCount == source.ImageCount && source.ImageCount > 0`。启动已完成镜像后，远端移动/改名、修改尺寸/mtime 或删除一项同时新增一项，数量仍相同，后续常规同步跳过所有照片分页，客户端继续使用陈旧路径与元数据。这是优化造成的一致性缺口，不只是速度问题。

建议：源变更版本/服务端修改水位，或真正增量事件；在缺少可信版本时不能只用 count 跳过。验收：两个客户端/两个隔离库，远端同数量移动和替换后不重启客户端即可看到新路径；已有人工元数据不回退。

### PERF-04 / P2：目录预览全库扫描和逐项查描述，快速选择累积无效工作

位置：`src/Picer.Core/Vision/DirectoryDescriptionPlan.cs:14-17`、`DirectoryMediaDescriptionPlan.cs:21-23`；窗口 `DirectoryMediaDescriptionWindow.cs:96-102`。每选择节点都读全库照片/视频，在内存过滤，再逐照片 `HasCurrentDescription`、逐视频 `HasCurrentSummary`。版本号只丢弃旧结果，不取消旧数据库作业；它们仍在唯一 `UiWork.DatabaseGate` 排队，阻塞新选择或其他编辑。

建议：可取消并短暂防抖的节点预览；SQL 层按规范路径/源过滤；一次查询有效描述状态；过期作业排队前后均退出。验收：10 万媒体、连续快速选 20 节点，记录最终预览延迟和废弃 SQL 次数，期间重命名标签仍及时完成。

### PERF-05 / P2：目录树在 UI 线程全量排序并创建控件

位置：`src/Picer.App/Views/DirectoryMediaDescriptionWindow.cs:55-58,67-90`。后台只是读所有媒体记录和提取路径，`PopulateDirectories(paths)` 回到 Dispatcher 后排序全部文件路径，并对每张照片重复拆分完整目录路径，创建所有目录的 TreeViewItem，无分批让出。目录数/文件数大时可造成窗口打开和输入响应停顿。

建议：数据库直接取 distinct 目录或后台构造去重树模型，根节点先显示、按展开懒加载子节点；加载期间可取消。验收：大量文件集中少量目录与大量小目录两类分别测 UI Dispatcher 最大停顿、首屏时间、控件数和分配字节。此处确认存在同步全量工作，具体卡顿时长待测。

### PERF-06 / P2：缩略图请求去重共享了第一个调用者的取消令牌

位置：`src/Picer.Core/Gateway/RemoteThumbnailCache.cs:54-63,79-81`。同内容两个可见卡片共享 Lazy<Task>，下载使用第一个卡片 token；第一个卡片因滚动离开被取消，会同时取消第二个仍可见卡片的下载。另每个等待者 finally 均按 key 无条件 TryRemove，旧等待者的延迟清理可能删除新一代在途条目，削弱去重。

建议：缓存拥有下载生命周期，调用者用 WaitAsync(token) 取消自己的等待；用 key+任务身份条件删除，必要时最后订阅者离开再取消底层请求。验收：两个等待者，取消首个时第二个仍成功；失败重试与旧 finally 交错时新下载仍只有一次。

### PERF-07 / P2：远端资源缓存全局串行下载且同步全文件哈希

位置：`src/Picer.Core/Gateway/RemoteAssetCache.cs:31-50,69-81`。单 `_gate` 覆盖完整下载、SHA-256 和淘汰；一个长视频阻塞不同内容照片下载。下载后的 `SHA256.HashData(verify)` 为同步调用且不接收 token，用户取消后仍可能等待大文件完整校验；每次下载淘汰都遍历全部缓存文件。

建议：每内容互斥加总字节/并发上限，容量提交独立短锁；异步可取消哈希；缓存目录索引或低频清理。不要无上限并行大视频。验收：慢视频与小照片并发时小照片不等视频；哈希阶段取消后短时退出，部分文件被清理；并发提交遵守容量上限。

### PERF-08 / P1（规模风险）：视频音频响应被全量内存复制并转 JSON 持久化

位置：`server/Picer.IndexService/ServiceTaskRunner.cs:35-38,58-65`。可重放范围含 GET video-audio；中间件捕获 MemoryStream，再 ToArray，再将 byte[] 作为 JSON base64 字符串整体序列化并写盘。长视频音频会同时占原始缓冲、复制数组和 JSON 字符串，多请求并发进一步放大；任务结果还需保存磁盘空间。

建议：流式临时文件结果缓存、分离小 JSON 元信息、明确结果 TTL 和容量、限制大任务并发，完成后原子提交；不要以禁止分块传输掩盖问题。验收：隔离数百 MB 响应、并发请求和取消，观察峰值托管堆、首字节延迟、磁盘配额及清理。机制确认，真实 OOM 阈值未测。

## 并发模型的跨专项风险

`PicerDatabase` 持有一个 `_conn`（`src/Picer.Core/Data/PicerDatabase.cs:12`），`UiWork` 的静态 DatabaseGate（`src/Picer.App/Infrastructure/UiWork.cs:10`）只保护显式经它的调用。一些窗口仍用裸 `Task.Run` 操作同一个 PeopleService/Database，例如 `PersonDetailWindow.xaml.cs:29,68,74,80,89`、`FaceDetailWindow.xaml.cs`。应与健壮性专项统一审查连接所有权；Task.Run 不能替代串行数据库访问。压力验收必须覆盖后台镜像同步同时进行人物合并、归类、描述保存；不把代码中有 SemaphoreSlim 当作全局线程安全已成立的证明。

`CloudVisionAnalysisService` 的内容 semaphore 字典按不同 hash 增长，没有逐项回收（`:21,47`）；目录窗口服务生命周期结束后可整体 GC，但长期服务或超大单次批次仍有 O(唯一内容数) 驻留。优先排查生命周期和峰值，不宜为回收贸然按 key 删除造成两个锁同时存在。

## 建议的隔离性能基线

1. 1k/10k/100k 合成索引；目录预览、增量未变化扫描、1% 新增修改、全校验分别记录数据库读取行数、耗时、分配及 UI 响应。
2. 同时启动浏览缩略图、照片/视频描述、镜像同步、取消，再按每类队列等待与执行耗时诊断；不能只测单任务平均吞吐。
3. watcher 注入异常/失效、目录重命名、扫描期间修改和分页取消；验证只能保守保留索引，不能因不完整枚举标 missing。
4. 所有压力素材和数据库放 artifacts 下，禁用真实模型与远端收费配置；原始用户数据和现有 P2 验收集不参与破坏性/压力试验。
