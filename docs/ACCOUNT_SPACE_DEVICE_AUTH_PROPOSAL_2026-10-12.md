# 跨电脑使用、账号空间与设备授权建议方案

日期：2026-10-12。状态：方案说明，详细契约以 [专项 SDD](ACCOUNT_SPACE_DEVICE_AUTH_SDD_2026-10-12.md) 为准。本文描述计划设计，当前 v1.4.0 尚未实现账号、多租户、授权文件或设备管理。既有发布与部署不因本文改变。

## 1. 推荐结论

采用“账号登录为主、指定设备授权文件为辅、照片空间隔离数据”的统一方案。普通用户在新电脑输入管理员提供的服务地址，登录后选择照片空间，即可读取已有索引。个人自建用户也可以用已授权电脑或管理门户批准新电脑，下载并导入文件完成接入，无需复制长期令牌或编辑配置。

保留纯本地模式，不强制注册和联网。GUI 安装包不嵌入某个生产服务的凭据；用户从 GitHub 获得下载权限，不代表已经拥有软件账号或照片空间。

## 2. 为什么不能只加一个“导出令牌”按钮

当前一个 IndexService 使用一个数据库和一个共用令牌。把它装入文件只能方便复制配置，不能区分用户、限制来源目录、撤销一台电脑，或隔离两人的搜索/缩略图/人脸数据。旧电脑的 DPAPI 配置只为本机用户保护，也不是可移植授权。

| 选项 | 使用体验 | 权限与数据边界 | 结论 |
| --- | --- | --- | --- |
| 导出当前共享令牌 | 操作少 | 复制即共享同等权限，丢失后所有设备换令牌 | 不采用 |
| 只加账号登录窗口 | 登录方便 | 底层仍共库、代理任取、缓存未隔离，无法保证独立用户数据 | 不能单独交付为多租户 |
| 每人单独部署一套服务 | 隔离清楚 | 每人维护端口、进程、升级与备份，运营成本增加 | 继续支持个人自建，但不是共享服务主方案 |
| 空间隔离＋独立设备授权 | 首次需选择空间与批准权限 | 可撤销单设备、多来源归属明确、可扩展家庭共享 | 推荐 |

首版采用每空间独立 SQLite 和缓存目录，控制库只管理账号/空间/设备/路由。与给所有旧业务表添加 tenant_id 相比，这更适合现有 SQLite、FTS、人脸和视频模型；仍必须改造授权入口、任务、缓存及 Agent 路由，分库本身不能代替授权。

## 3. 用户实际怎样使用

### 情形 A：同一用户更换电脑

1. A 保持本地功能，明确选择“启用同步”、服务地址、账号、照片空间和目录。
2. A 的索引/获准元数据后台同步；原照片和视频仍在 A，Agent 仅提供获准目录。
3. B 安装 GUI，输入同一服务地址并登录，选择空间。
4. B 先显示首批索引和缩略图，后台继续镜像；不启动本机 Agent、不下载模型。
5. A 离线时，B 可使用已有索引/缓存，原图或视频提示来源离线。

### 情形 B：希望“下载授权文件，导入即可”

1. B 在线创建配对申请，私钥留在 B，导出申请文件或二维码。
2. 用户在 A 或管理门户登录，核对申请，选空间/权限并批准。
3. 下载 `.picer-auth`，在 B 导入并验证服务身份，兑换 B 独立的设备凭据。
4. 文件只对 B 的密钥有效，只能兑换一次；正常导入无需手填 token。

首版申请必须在线生成；文件可以通过 U 盘等方式搬运，但兑换仍需联网。申请和批准后的文件分别计时 15 分钟，过期重新申请/批准。没有 B 的申请时，门户可下载无秘密的服务连接配置，导入后仍需登录，不发行任意持有者可永久使用的通行文件。自签名服务首次需要可信渠道核对身份；短设备校验码不能代替服务证书指纹。

### 情形 C：家庭或多个独立用户

家庭可以共享一个空间，通过成员角色区分查看、编辑和管理；不相关用户使用不同空间。一个账号可加入多个空间。邀请成员和批准设备是不同操作：Owner 批准 Viewer 的电脑，电脑仍属于 Viewer，不能继承 Owner 身份。

远程查看、原媒体读取、模型调用、来源索引发布和彻底清除分别授权。新增来源必须在源机确认目录；登录账号或安装 GUI 不等于启用源代理。

## 4. 必须同时完成的工程范围

| 领域 | 交付内容 |
| --- | --- |
| 身份 | 浏览器登录、本地自建 Owner、恢复码、设备会话、续期和单设备撤销 |
| 数据 | 每空间独立数据库/FTS/缓存；全局身份；同内容多引用；克隆库新来源识别 |
| 同步 | 原子 outbox、快照切点、逐项确认、冲突和 epoch；断网/崩溃可恢复 |
| 来源 | 设备绑定的 AgentGrant、sourceId 精确路由、目录授权及来源迁移 |
| 媒体与模型 | 连接池、租约、任务、AI预算、训练制品和诊断全链路隔离 |
| 体验 | 服务地址入口、登录选空间、文件配对、设备管理、离线与过期说明 |
| 运维 | 旧库迁移、证书/密钥轮换、旧客户端阻断、闭库备份和恢复屏障 |
| 性能 | 受限队列、空间公平调度、前台数据库槽、控制面保留容量和磁盘余量 |

不存在“只做授权文件就完成全部目标”的安全捷径。详细工作包 M0～M6、协议与验收 T01～T22 见专项 SDD；这些是新设计范围，不是恢复此前暂停的质量/硬件 P2 事项。

## 5. 关键取舍与用户影响

- **严格清除**：按用户要求不保留被清媒体索引或墓碑。为阻止离线旧数据复活，清除批次会更新空间代际并重建各设备基线；这比保留删除 ID 的协议成本更高。已收到清除通知的客户端不能继续显示旧远程镜像。
- **备份恢复**：独立的空间级恢复屏障不记录媒体内容，但会使清除前整库备份不能直接恢复上线。无法证明屏障最新时宁可拒绝恢复，不能悄悄复活已清内容。
- **撤销边界**：可以停止新访问和活动流，不能收回恶意复制的文件或保证长期离线设备擦除缓存；产品提示必须说明。
- **离线能力**：本地功能不受账号影响。远程缓存离线查看受空间策略控制；模型上传、同步和来源目录授权分别确认。
- **容量**：首版单服务进程和空间分库，先保证公平与有界资源，不声称已实现横向多活；性能数字是待验收预算。

## 6. 实施与发布策略

先完成认证/控制库及双空间隔离，再落地来源身份和事务同步；配对 UI 可以并行开发，但不能先作为“多用户版”正式发布。旧数据在闭库备份后迁移到一个明确归属的 legacy-space，不能自动猜测旧数据属于哪个人；旧 shared token 不能认领 Owner。

发布前必须有干净电脑 A/B 接入、双空间越权、并发兑换、撤销竞态、严格清除与旧备份恢复、源电脑离线、视频读取及故障注入证据。完成设计评审不等于代码通过这些测试；现有 v1.4.0 的 CI 数量不能充当新功能验收。

本次只完成设计与专家评审，不改变现有服务认证、数据库或运行程序。后续开发以专项 SDD 为契约，以[评审汇总](ACCOUNT_SPACE_DEVICE_AUTH_REVIEW_2026-10-12.md)跟踪设计问题及关闭依据。
