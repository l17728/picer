# Picer 产品与体验设计

版本：1.2
状态：人物与复合视觉检索设计基线  
更新时间：2026-09-01

## 1. 产品定位

Picer 是一款本地优先的图片检索与整理工具，帮助用户在不改变原始图片的前提下建立索引、搜索和问答、添加标签，并识别完全重复或视觉相似的图片。

### 1.1 核心价值

- 快速找到图片：支持关键词、元数据、标签、目录和自然语言问答。
- 理解图片内容：识别场景并给出可解释、可接受或拒绝的标签建议。
- 辅助清理图库：发现完全重复和视觉相似图片，但由用户决定保留或删除。
- 尊重文件所有权：默认只读，不主动移动、覆盖、重命名或删除原文件。

### 1.2 产品安全原则

以下原则优先于任何功能便利性：

1. 扫描、检索、问答、打标和重复识别不得修改原文件。
2. 系统不得根据“最大、最新、最早、最高分辨率”等规则自动删除文件；这些规则只能生成建议。
3. 删除原文件必须由用户逐项或逐组明确选择，并在执行前再次确认。
4. “从索引移除”“移到系统回收站”“永久删除”必须使用不同术语和操作入口。
5. 默认删除方式是移到系统回收站；首个版本不提供永久删除。
6. 任何无法确认结果的操作都不得显示“已删除”或“已释放空间”。
7. 对缺失文件重新定位时，必须校验文件身份；不得仅凭扩展名重新绑定。

## 2. 目标用户与核心任务

### 2.1 目标用户

- 拥有数万至百万张本地图片的摄影用户。
- 需要整理家庭照片、工作素材或历史归档的普通用户。
- 使用本地磁盘、移动硬盘、NAS 或 WebDAV 保存图片的用户。
- 重视隐私，不希望默认上传图片内容到云端的用户。

### 2.2 核心用户任务

1. 添加图片来源并建立索引。
2. 按时间、目录、相机、尺寸、标签或文字搜索图片。
3. 使用自然语言提问并查看命中依据。
4. 查看、接受、修改或拒绝识别标签。
5. 检查完全重复和视觉相似图片。
6. 明确选择每组中的保留项及待删除项。
7. 将经确认的文件移到回收站，或保持不处理。
8. 定位已经移动的文件并安全恢复索引关系。

## 3. 信息架构

主窗口采用“导航—内容—检查器”结构：

- 左侧导航：全部照片、时间线、文件夹、标签、相册、重复与相似、缺失项目。
- 顶部全局区：统一搜索/问答框、筛选条件、当前后台任务。
- 中央内容：虚拟化照片网格、搜索结果或专项工作台。
- 右侧检查器：所选照片详情、标签、来源、命中依据和文件操作。
- 底部任务入口：索引进度和错误摘要；技术日志默认折叠。

维护操作如重建索引、缓存管理和诊断日志进入“设置/维护”，不与日常浏览操作混排。

## 4. 关键体验流程

### 4.1 首次使用与建库

空库只展示一个主操作“添加照片文件夹”，并明确说明：

> Picer 只建立索引，不移动或修改原始图片。

选择目录后先展示扫描计划：路径、可识别图片数、已存在数、不可读取数及来源类型。用户确认后仅索引新增来源。索引期间展示阶段、完成比例、已处理数量、耗时和取消按钮；取消后保留已完成且一致的数据。

### 4.2 浏览与搜索

- 默认以可缩放的虚拟化缩略图网格展示图片。
- 支持时间分组、键盘连续导航、多选和右键菜单。
- 全局搜索框同时承载结构化检索和自然语言问答，但必须明确当前模式。
- 筛选项包括日期、相机、尺寸、文件大小、来源、标签和缺失状态。
- 已启用筛选以 chips 展示，可逐项清除。
- 结果区同时显示匹配总数和当前加载数，不得静默截断。
- 无结果时说明搜索范围，并提供清除筛选或调整查询的建议。

### 4.3 标签与识别

- 用户标签和 AI 建议标签在视觉及数据模型上明确区分。
- AI 标签必须展示建议来源或置信度，支持接受、拒绝、编辑和批量处理。
- 接受标签只修改 Picer 数据库；除非未来另行设计并显式授权，否则不写回 EXIF/XMP。
- 问答结果显示命中依据，例如标签、文件名、时间、地点或识别内容。

### 4.4 重复与相似图片

系统将结果分为：

- 完全重复：内容 SHA-256 一致。
- 视觉相似：感知哈希达到阈值，可能包含连拍、裁剪或不同导出版本。

每个结果组展示缩略图、完整路径、文件大小、分辨率、拍摄/修改时间、来源及相似度。系统可以推荐保留项，但不得代替用户选择。

状态模型：

- 未决定
- 建议保留
- 用户选择保留
- 用户选择删除
- 暂不处理

工作流：

1. 用户运行识别并选择范围。
2. 系统生成候选组，不改变文件或索引。
3. 用户逐组检查并选择保留/删除项。
4. “检查删除方案”汇总文件数、路径、容量和冲突。
5. 用户二次确认后，待删除文件移入系统回收站。
6. 执行完成后逐项核验，并展示成功、失败、实际释放空间和恢复说明。

关闭窗口、取消或保持“未决定”不得产生任何文件变化。

### 4.5 缺失文件恢复

- 支持定位单个文件和指定新的根目录进行批量匹配。
- 默认使用已有 SHA-256 校验身份；相同哈希、不同路径可以恢复。
- 哈希不同必须阻止自动绑定。
- 如未来支持绑定不同内容，应命名为“强制重新关联”，要求单独确认并重建所有派生数据。
- 扫描失败、网络错误或权限错误不得被解释为文件缺失。

## 5. 交互与无障碍规范

- `Ctrl+F` 聚焦搜索，`Esc` 清空/退出当前模式，`Enter` 打开，方向键导航，`Ctrl+A` 全选。
- 删除键只进入受保护的删除方案，不得立即修改文件。
- 所有图片项具有可访问名称：文件名、日期、状态。
- 状态不能仅依赖颜色，须同时使用文字或图标。
- 正文目标字号不低于 12–14px，并验证高 DPI 和 WCAG AA 对比度。
- 后台任务运行时禁用冲突操作，失败必须提供用户可行动的说明。

## 6. 性能体验预算

以下是 Picer 的产品目标，不是竞品公开成绩：

| 场景 | 目标 |
|---|---|
| 10 万图片冷启动首窗 p95 | < 1.5 秒 |
| 10 万图片完全可交互 | < 2.5 秒 |
| 10 万索引搜索反馈 p95 | < 150ms |
| 100 万索引搜索反馈 p95 | < 300ms |
| 首屏 50 张缓存缩略图 | < 500ms |
| 本地未缓存首屏缩略图 | < 1.5 秒 |
| 取消操作的界面反馈 | < 100ms |
| 后台工作实际停止 | < 1 秒 |
| 10 万图库空闲工作集 | < 500MB |
| 滚动长帧（>50ms）占比 | < 1% |

## 7. 成功指标

- 新用户无需说明即可完成首次建库。
- 用户始终能够判断 Picer 是否会修改原文件。
- 重复识别到删除确认之间不存在未经用户选择的文件操作。
- 搜索结果不静默截断，失败和部分完成状态可理解、可恢复。
- 10 万图片基准库达到第 6 节性能预算。

## 8. 本阶段不做

- 未经用户逐项选择和二次确认的自动删除、自动移动或自动重命名原文件。浏览删除仅将明确选中的文件移入 Windows 回收站，失败项保留索引。
- 绕过回收站的永久删除。
- 默认写回 EXIF/XMP。
- 未经明确授权的图片内容云端上传。
- 把视觉相似结果直接认定为完全重复。

## 9. 本地人物与复合视觉检索

### 9.1 目标与边界

目标是让用户组合人物、地点、时间、服饰和场景条件，例如：

> 找一下老婆在商洛的照片，夏天穿裙子，在山上。

系统把问题转换为可解释的结构化条件并返回交集结果。人物和视觉分析默认在本机完成，原图、人脸裁剪和人脸特征不发送到外部服务。

本能力不用于公共场所身份识别、陌生人实名推断或年龄、种族、健康等敏感属性判断。Picer 只在用户自己的图库中聚类相似人脸；算法产生“人物候选”，真实身份和关系别名必须由用户确认。

### 9.2 人物建立流程

1. 用户显式启动“分析人物”，选择来源和范围；普通建库不默认执行高成本人脸分析。
2. 系统本地检测人脸、计算不可逆特征向量，并形成待确认人物组。
3. 人物组展示代表照片、候选数量、时间跨度和来源，不预填真实姓名。
4. 用户可执行“命名、合并、拆分、不是同一人、忽略、暂不处理”。命名只写入 Picer 数据库。
5. 人物可设置规范名称和别名，例如规范名称“李某”、关系别名“老婆”；别名仅属于当前本地资料库。
6. 新照片只生成候选匹配；低置信度结果进入待审阅队列，不自动归入已命名人物。

删除人物名称默认只删除名称、别名和关联；“清除人物识别数据”单独删除人脸特征。两者均不得删除原始照片。

### 9.3 人物工作台

新增“人物”导航页：

- 已命名人物：名称、别名、照片数和最近拍摄时间。
- 待确认人物：支持批量确认、合并和拆分。
- 未归类人脸：质量不足或无法可靠聚类的候选。
- 忽略的人脸：可恢复，适合海报、屏幕、雕像或误检。

人物详情页显示照片网格、命中置信度和“不是此人”的纠错入口。用户确认的身份关系优先于后续模型重跑，不得被自动聚类覆盖。

#### 多人照片交互

- 一张照片可以包含零到多张独立人脸；人物归属绑定到具体人脸，不绑定整张照片。
- 照片详情显示可开关的人脸框，并在下方显示按画面从左到右排列的人脸头像条；选择头像时只高亮对应人脸，原图不移动、不重新排序。
- 每张脸分别显示“已确认人物”“可能是”“未归类”或“已忽略”，支持逐脸命名、确认、“不是此人”、移动到其他人物和忽略误检。
- 合影支持一次选择多张脸并批量标为同一人物候选，但提交前逐张显示，避免把同行者全部覆盖成一个名字。
- 同一照片中的两张不同人脸默认不得自动归入同一人物；只有用户明确确认，或分别通过高阈值匹配后才允许。
- 人物搜索采用照片级存在语义：照片中任意一张已确认人脸属于目标人物即命中；查询“甲和乙”要求同一照片同时存在甲、乙两人的已确认人脸。
- 纠错只改变所选人脸的归属，不影响同一照片中的其他脸、照片标签、相册或原文件。

### 9.4 视觉建议标签

本地视觉模型可产生：

- 场景：山地、海边、公园、室内、城市、道路等。
- 服饰：裙子、外套、帽子等可见服饰，不推断职业、宗教或社会身份。
- 活动与物体：聚餐、徒步、车辆、宠物等。
- 季节：优先根据拍摄日期和地点计算，视觉季节只作低置信度补充。

模型输出始终是建议，保存模型名称、版本和置信度。用户可以接受、拒绝或修正；拒绝结果在同一模型版本下不重复出现。

### 9.5 复合查询

| 原句片段 | 结构化条件 | 依据 |
|---|---|---|
| 老婆 | `person_id = 已命名人物` | 用户设置的关系别名 |
| 在商洛 | `gps within 商洛市边界` | EXIF GPS 与地域边界 |
| 夏天 | `taken_month in 6..8` | 拍摄时间；按地点半球调整 |
| 穿裙子 | `visual_tag = apparel.dress` | 本地视觉模型及置信度 |
| 在山上 | `visual_tag = scene.mountain` | 本地视觉模型及置信度 |

默认以 `AND` 求交。零结果时逐项显示人物、地点、时间和视觉条件的命中数，以及从哪项开始交集为零，并允许用户一键放宽单项条件。

每个结果显示命中依据，例如“人物：老婆 0.91；地点：商洛市；日期：2023-07-18；服饰：裙子 0.78；场景：山地 0.84”。置信度不得表述为确定事实；无法解析的条件必须明确标为不支持，而不是伪装成零结果。

### 9.6 隐私与授权

- 人脸特征属于敏感派生数据，只保存在当前 Picer 数据目录。
- 默认不调用云端人脸、大模型或视觉 API；未来的云端选项必须逐次说明发送内容、服务商和保留政策，并取得显式授权。
- 地理编码仅发送用户主动查询的地名或单张照片坐标，不发送图片、人物名称、文件路径或复合查询全文。
- 日志、遥测和崩溃报告不得包含人脸裁剪、特征向量或人物真实名称。
- 备份和导出必须让用户明确选择是否包含人物识别数据。
- 提供“一键清除人物与视觉识别数据”，只清除派生索引，不影响标签、相册和原始文件。

### 9.7 性能预算

| 场景 | 目标 |
|---|---|
| 人脸分析取消后的实际停止 | < 2 秒 |
| 已索引人物筛选 p95 | < 150 ms（10 万图片） |
| 五条件复合查询 p95 | < 300 ms（10 万图片） |
| 人物页首屏 | < 1 秒（缓存代表图） |
| 后台分析时前台滚动帧长 >50 ms 占比 | < 1% |
| 人脸/视觉模型峰值工作集 | 不超过既有预算的 1.5 倍 |

分析任务支持暂停、继续、取消、断点续作和模型升级后的增量重算；电池供电或前台高负载时默认降低优先级。

### 9.8 验收标准

- 用户能命名人物候选组，并通过名称或别名检索。
- 合并、拆分和“不是此人”可撤销，且不修改原图。
- 复合查询返回结构化解析、逐项命中数、结果依据和置信度。
- 测试集分别报告人脸检测召回率、错误合并率、错误归人率和未知人物拒识率。
- 不含 GPS、拍摄时间或可用人脸的照片不会被虚构地点、季节或身份。
- 断网时人物、时间、已缓存地域和视觉标签检索仍可使用。

## 10. AI 问答文本检索层（规划）

### 10.1 目标

所有由 Picer、用户或模型生成且具有检索价值的文字，都应成为后续本地 AI 问答的可检索知识，而不是只显示在某个页面。首期采用“BM25 召回候选文本 → 根据稳定定位符取回完整记录 → 本地语言大模型判断并组织回答”的检索增强生成流程。

AI 问答使用本地语言模型；检索、完整记录取回和最终判断默认不向云端发送。现有云端多模态服务只负责用户明确授权的照片描述、场景总结或视频分析，不自动获得问答全文。

### 10.2 纳入检索的文字

至少包括：

- 单张照片描述，以及对应的场景、活动、物体和搜索词；
- 用户接受的场景名称、场景整体摘要和场景搜索词；
- 视频摘要、本地语音转写和关键帧分析摘要；
- 用户标签、相册名称与相册描述；
- 已确认人物名称与别名，但必须遵守本地敏感数据边界；
- 文件名、相机信息、拍摄时间、地点文字和行政区划；
- 后续新增的 OCR 文本、用户备注和其他明确标记为可检索的派生文字。

统一标签投影还必须覆盖 Picer 对照片和视频形成的全部组织维度：

- 人物标签：用户已确认的人物名称、别名，以及照片或视频关键帧与人物的已确认关联；
- 场景标签：单张照片识别场景、用户接受的分类场景名称、场景摘要及其搜索词；
- 地域标签：国家、省、自治区/州、市、县、区、镇、乡、村、地点文字和用户修正地点；
- 时间标签：年、月、日、周、季节、时间线相册与时间锚点；
- 组织标签：来源目录、子目录、相册、时间相册和用户自定义集合；
- 媒体标签：照片或视频、相机/设备、尺寸、格式及其他可解释元数据；
- 内容标签：用户标签、已接受模型标签、OCR、照片描述、视频转写、视频摘要和关键帧描述。

这些标签既进入 BM25 可检索文本，也作为结构化过滤字段保留。用户询问“2023年在西安和张三一起拍的聚餐视频”时，可以先用时间、地域、人物和媒体类型缩小范围，再用 BM25 检索“聚餐”等内容词。人物分析尚未确认的候选组不能作为确定的人物标签进入问答事实。

被用户拒绝、已失效、已删除或仅属于临时推理过程的文字不得进入有效问答语料。模型原始建议与用户确认内容必须保留来源和状态，回答时优先采用用户确认内容。

### 10.3 用户体验

1. 用户输入自然语言问题。
2. Picer 在本地文本索引中召回有限数量的候选记录，并可叠加人物、时间、地点、目录或相册过滤条件。
3. 系统通过候选记录的稳定定位符取得完整照片描述、完整场景总结、完整视频摘要等信息；不得只把被截断的命中片段交给模型。
4. 本地语言模型基于完整记录判断相关性、合并重复事实并生成回答。
5. 回答必须显示依据，用户可点击依据定位到对应照片、场景节点、视频、相册或人物。
6. 没有足够依据时明确回答“未找到足够信息”，不得根据模型常识虚构图库事实。

示例：用户询问“哪次聚餐有穿校服的学生？”时，BM25 可先命中照片描述中的“校服、学生、餐厅、聚餐”，再取回相邻代表照片和所属场景的完整总结，由本地模型判断并返回可点击的场景与照片。

### 10.4 检索与排序原则

- BM25 负责第一阶段关键词召回，不直接等同于最终答案相关性。
- 中文查询与文档使用同一分词/规范化版本；文件名、地点、型号和人物别名保留精确词。
- 一个候选命中后，完整取回其规范记录，并可按所属场景、视频或相册补充有限的上下文记录。
- 默认限制候选数和提交给模型的总字符数，避免大图库问答造成长时间阻塞或内存峰值。
- 后续可加入本地向量召回并与 BM25 融合，但不能替代稳定定位、来源说明和用户确认状态。

### 10.5 增量性与一致性

- 新增或更新照片描述、场景总结、视频摘要、转写、标签、人物名称、地点信息时，只更新对应文本记录。
- 内容不变时通过内容哈希跳过重建；模型版本或提示词变化但最终文字不变时同样不重复写入。
- 删除相册只移除相册关联文字，不删除照片文字；移除索引源或清理派生分析时同步使对应问答文档失效。
- 问答索引可从规范业务表完整重建，不能成为照片描述或用户确认结果的唯一存储位置。

照片和视频遵循完全相同的增量投影机制。人物归属、地点、时间线、场景分类或标签发生变化时，只更新受影响媒体及其父场景/视频文档；不得重新调用大模型，也不得重建整个媒体库。视频关键帧的人物和场景标签应汇总到视频级检索文档，同时保留关键帧时间码，以便回答依据定位到视频中的具体位置。

### 10.6 验收标准

- 照片描述、场景总结和视频摘要写入后可通过关键词召回，无需全库重新分析。
- BM25 命中结果可以稳定定位并取回一条完整规范记录。
- 本地模型收到的上下文包含来源类型、稳定 ID、完整正文和必要的时间/地点元数据。
- 回答依据可点击返回对应 UI 对象；对象失效时显示明确状态而不是打开错误对象。
- 断网环境下文本检索与本地 AI 问答完整可用。
- 用户拒绝或删除的派生文字不再出现在新回答中。
- 已确认人物、地域层级、时间线、目录、相册和分类场景可以单独或组合检索照片与视频。
- 视频摘要、转写、关键帧描述和关键帧人物标签可以召回视频，并能定位到视频或具体时间码。
