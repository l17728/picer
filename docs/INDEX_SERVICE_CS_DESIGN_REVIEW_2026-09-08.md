## 总体结论

**有条件通过——架构方向正确，可批准 P1 开发。**

1. 与 SDD 不变量的映射完整：只读边界、单写入器、状态机归属、隐私约束在 C/S 拓扑下均保持成立。
2. "构建在服务、客户端只授权与消费"的核心决策论证充分，反向方案（GUI 构建/服务存储、客户端数据中转）的否决理由成立。
3. 哈希身份锚点 + 内容层/物理层拆分正确回应了"移动/重导入丢关联"的产品需求，且迁移可独立先行。
4. 评审发现的全部"修订"级问题已在本文档同步落实（见汇总表），无遗留阻断项。

## E1 服务边界与演进架构师

评审范围：进程边界、部署形态、传输选择、API 演进、多客户端一致性。

认可点：

- 传输无关的端点处理器 + 三传输共享（§3 原则 3、§5.1）避免了"每形态一套 API"的漂移。
- "任一时刻只有一个构建者，禁止双写"（§3 原则 2）是防止 local/service 数据分叉的关键约束，且配了迁移交接路径（§6.2）。
- P1 明确"服务模式只读、不提供混合读写"（§11），避免了同一图库双 owner 的过渡态陷阱。

发现：

- E1-1【修订·已落实】原 P1 表述"写仍走 local"与只读服务化并存即双 owner。已改为 P1 只读交付。
- E1-2【修订·已落实】多客户端并发写逻辑数据的冲突语义原缺失。已补 §5.2 约束 5：单写入器顺序化 = 字段级 last-writer-wins + 领域事件通知刷新。
- E1-3【备忘→P3】API 兼容承诺缺失：`/api/gateway/v1` 需声明向后兼容窗口；`/health` 增发 `schemaVersion` 与 `minClientVersion`，GUI/服务解耦升级需要版本矩阵。
- E1-4【备忘→P2】任务进度目前轮询 `/jobs/{id}`，多客户端规模大时评估 SSE；先轮询交付。

## E2 安全与隐私专家

评审范围：认证、凭据委派、传输安全、威胁模型、生物识别数据约束（SDD §7/§11.7）。

认可点：

- 客户端作为"授权桥梁而非数据桥梁"（§4.1）使授权清单（来源列表）与数据可达性严格一致，撤销语义清晰。
- 凭据服务侧仅存凭据管理器/DPAPI、审计不含凭据值（§4.1、§9.6）符合现有隐私基线。
- 跨机 = 独立授权点 + 二次确认（§5.1、§9.3），与 SDD"外发前独立授权"对齐。

发现：

- E2-1【修订·已落实】token 原设计明文写入 `service-endpoint.json`。已改为 DPAPI（CurrentUser）加密后落盘（§5.1）。
- E2-2【修订·已落实】威胁模型未显式声明。已补 §5.1 注记：同用户本地进程为可信边界；管道帧不加密；token/ACL 为纵深防御。
- E2-3【修订·已落实】跨机 TOFU 首连可被同主机恶意服务抢占。已补 §5.1：配对 UI 显示证书 SPKI 指纹人工核对。
- E2-4【备忘→P2 评审】人脸向量为生物识别数据：远程模式"仅下发 personId、名称按授权规则"（§9.4）已符合基线；P2 实现时增加代理测试断言（§10.6 已覆盖）。
- E2-5【备忘】WebDAV 凭据经管道明文帧一次性传输：与"同用户可信边界"一致，可接受；实现时避免凭据进入任何日志与异常文本。

## E3 数据工程 / SQLite 专家

评审范围：内容层/物理层模型、v30 迁移、FTS 投影、并发与恢复。

认可点：

- 内容稳定事实与物理事实的划分（§4.5）边界清晰，"人工确认属于内容不属于路径"正确。
- 感知哈希不参与身份判定、`content_hash_state=failed` 不做关联决策（§4.5）避免了脏关联。
- 重关联全部为可逆更新、结构化日志可审计（§4.5）。

发现：

- E3-1【修订·已落实】百万行级外键改挂需要分批短事务、可断点、失败整体还原备份。已写入 §11 P2。
- E3-2【修订·已落实】文本投影键（image_id vs sha256）原未定义。已补 §4.5：索引挂内容层、展示经物理 join。
- E3-3【备忘→P3】备份/恢复目前是 GUI 本地根假设（`DataProtectionService`）；service 模式需 API 化（§11 P3 已列，§13 M11）。
- E3-4【备忘→P2】同内容多副本时重复检测分组应按内容层合并（跨路径天然一组）；纳入 P2 验收用例（§10.4 已含双路径共享断言）。
- E3-5【备忘】首扫 SHA-256 成本与失败重试沿用现有流水线语义，无变更；确认 JobManager 不引入二次哈希。

## E4 WPF 客户端架构师

评审范围：客户端改造面、静态服务定位器、UI/UX 连贯性、打包。

认可点：

- §13 以逐文件核对给出消费面量化（`AppServices.*` 60+ 处、`MainViewModel` 33 处），改造范围可信。
- 策略 A（适配层先行）→ 策略 B（渐进注入）的两步走把最大风险隔开（§13.2）。
- 离线降级三态（服务未启动/网络分区/维护态）有明确 UI 文案要求（§6.3）。

发现：

- E4-1【修订·已落实】原稿未定义静态定位器的迁移策略。已补 §13.2。
- E4-2【备忘→P2】"关窗后扫描继续"是行为变化：设置页与首次切换向导必须明示，否则用户误以为异常。
- E4-3【备忘→决策】安装包双形态（GUI 精简/服务完整）挂 §12 开放问题，P3 前决策。

## E5 性能专家

评审范围：预算合理性、传输开销、扫描吞吐、内存。

认可点：

- 预算给出依据链（现有 SQL 预算 + 传输余量），且"契约测试断言行为一致而非性能一致"（§8）切分正确。
- 哈希命中重关联预算绑定"零哈希重算、零模型推理"断言（§8、§10.4），可机械化验收。

发现：

- E5-1【备忘→P1】列表/搜索 JSON 载荷先量基线再决定 gzip/MessagePack，避免过早优化。
- E5-2【备忘→P3】扫描吞吐 <10% 目标的度量口径按传输分别报告（管道/HTTPS/直调）。
- E5-3【备忘】缩略图 304 + 客户端 LRU 语义沿用 PERF-004，HTTP 模式重跑即可。

## E6 测试与交付专家

评审范围：契约测试、回归覆盖、混沌场景、阶段计划可验收性。

认可点：

- 三传输契约测试作为"防漂移"主闸门（§10.1）是本设计最重要的质量机制。
- 阶段退出条件均可机械化判定（契约全绿/预算达标/断点续作可验证）。

发现：

- E6-1【修订·已落实】原稿契约测试只覆盖两个实现。已改为三传输（§10.1）。
- E6-2【修订·已落实】混沌场景缺失。已补 §10.5（杀进程 WAL 恢复、分区降级恢复、磁盘满/凭据失效显式错误）。
- E6-3【备忘→P2】E2E 服务进程生命周期脚手架（启动/等健康/清理）是新增测试基建，工作量不可忽略（§10.8、§13 N6）。
- E6-4【备忘→P3】版本兼容矩阵与 `/health.minClientVersion` 验收（与 E1-3 合并）。
