## 根因

- WPF 提交命令在 UI 线程继续执行异步方法的同步前缀；问答服务在首个网络 `await` 前会访问 SQLite。数据库或人物索引较大时，提交后 UI 会短暂冻结。
- 进度只在模型规划请求发出前上报一次“理解问题 5%”。规划阶段可能等待远端 IndexService/模型服务数分钟，用户看起来像永久卡死。
- 每次规划还会同步读取并把所有已确认人物名放入提示词，增加数据库读取和请求上下文；人物身份实际上由本地人工确认索引权威核对，不需要传输整份名单。
- Chat 客户端默认超时为数分钟，单独的规划/复核阶段没有清晰、较短的超时反馈。

## 修复

- WPF 将完整 `AskAsync` 调度到后台线程，避免 SQLite 同步前缀占用 Dispatcher。
- 删除整份人物名清单的读取与提示词注入；规划器只抽取问题中明确提及的人名，最终身份约束仍在本地确认索引执行。
- 规划与候选复核各增加阶段状态、每 3 秒等待心跳和 90 秒独立超时。用户取消仍按取消处理，服务无响应会显示超时错误并写入阶段耗时日志。

## 回归

- `AiMediaRetrievalTests.SlowPlannerReportsWaitingStateAndTimesOutInsteadOfStallingAtInitialProgress` 使用永不返回的模型端点，验证请求等待状态可见、取消超时生效并产生明确错误。
- 既有 AI 检索测试覆盖人物约束、多人交集与模型复核结果。
- 验证 WPF 编译和 `git diff --check`。
