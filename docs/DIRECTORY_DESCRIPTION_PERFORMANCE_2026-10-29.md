# 目录照片与视频描述：调用链和性能排查

日期：2026-10-29。按用户要求，由独立子代理只读分析代码、现有 GUI/MediaAgent 日志及本机镜像中的轻量查询。本报告不代表已经完成性能修复或端到端验收。没有中止 GUI/服务、调用真实模型、迁移数据库、写入生产数据或发布版本。诊断脚本临时放在 E 盘；本次仓库只新增此报告。

## 结论

已有描述在发现阶段通过本地分页 SQL 批量判定，命中后直接跳过，不进入分析队列，不读取原图或关键帧，不做地理编码，也不调用模型。这个路径的工作量远小于重新描述，但现场不能承诺“全库瞬间跳过”：本次查询抽样有明显长尾，同时有描述任务与开发构建负载，尚未完成受控的全库纯跳过测试。

实际描述的耗时不能简单归因于网络。现有 MediaAgent 日志显示，模型上游完整请求通常需要数秒；媒体准备/编码存在数秒乃至数十秒的长尾。普通本机状态查询通常几十毫秒，也有个别慢读。当前日志缺少贯穿三端的同一个目录任务/条目关联 ID，不能把不同通道的中位数相减当作纯网络耗时。

## 调用链

### 发现与跳过

1. `src/Picer.App/Views/DirectoryMediaDescriptionWindow.cs:260` 创建 `DirectoryDescriptionDiscovery.DiscoverAsync`。
2. `src/Picer.Core/Vision/DirectoryDescriptionDiscovery.cs:26` 为照片、视频各开一个独立本机数据库连接；先记录高水位，再以路径和 ID 的 keyset 游标读取，每页最多 128 条。只读索引，不枚举原始媒体目录。
3. `src/Picer.Core/Data/PicerDatabase.DescriptionStream.cs:10` 通过目录表达式索引读取范围；`:47` / `:51` 调用批量有效描述判定。
4. 照片判定在 `src/Picer.Core/Vision/CloudVisionRepository.Directory.cs:15`：检查当前描述的大小/修改时间及可复用的内容派生证据。视频判定在 `src/Picer.Core/Video/VideoIndexService.cs:55`：通过内容 ID、摘要和文件版本判断。
5. `src/Picer.App/Infrastructure/MediaDescriptionBatch.cs:107` 对 `Described=true` 直接 `continue`，每 32 个跳过项更新一次进度。仅未描述项目进入工作队列。

已描述项目的网络请求数为 **0**，模型调用数为 **0**。按目前全库 8603 照片、529 视频估算，完整范围约 73 个非空页，另有终止页和高水位读取；批量判定没有退化为每个媒体一次 HTTP 请求。初次发现以外，执行前的二次状态检查用于处理发现后刚完成的结果，不能一概删除。

混合目录还存在有意的背压：未描述队列容量为 8192，超过容量时发现生产者会等候分析消费。因此“跳过数字还在增长”不一定意味着跳过查询本身在调用模型，也可能是前面的待描述项目占满队列。

### 新照片描述

`DirectoryMediaDescriptionWindow.cs:211` 本机只读快照再次检查已有结果 → `CloudVisionAnalysisService.cs:49` 内容级互斥及位置解析 → `:52` 当前模型/提示/位置指纹检查 → 预算预留和排队持久化 → `MediaDescriptionBatch.PhotoInputAnalyzer` 获取已核验分析图或授权原图 → 图像处理 → 模型 → 短数据库保存 → 描述同步队列。

远程模式下主要数据流为：

```text
GUI → IndexService → 来源 MediaAgent：请求核验的分析图
GUI ← IndexService ← 来源 MediaAgent：取得缩小、去元数据的图像
GUI → IndexService → 模型 MediaAgent → 已配置模型端点：视觉请求
GUI ← IndexService ← 模型 MediaAgent ← 模型：结果
GUI 本机持久化 → 异步上传及回读核对
```

`AppServices.cs:747` 已识别目录描述的私有分析输入缓存，可以直接复用，避免第二次相同远程取图。它不是完全消除图像处理：`OpenAiCompatibleCloudVisionAnalyzer.cs:168` 仍会解码、去元数据并 JPEG 编码，已准备好的 JPEG 也经过此路径。

GPS 未缓存时，`CloudVisionAnalysisService.cs:111` 会调用反向地理编码。`NominatimReverseGeocoder.cs:81` 有进程级串行门和至少一秒请求间隔，HTTP 超时为十秒；失败响应可能进入第二地理服务。缓存命中则不请求网络。目录发现已经跳过的媒体不会走到这里；其他直接调用 `CloudVisionAnalysisService` 的路径，是先解析位置才检查模型指纹，不能混同两者。

### 新视频描述

`DirectoryMediaDescriptionWindow.cs:233` 再查摘要 → `:234` 读取关键帧元数据 → 无帧时请求来源端提取并保存 → `:246` 物化远程关键帧 → `VideoSummaryService.cs:51` 内容级摘要复用检查 → `:76` 取最多 12 个可用帧 → `:84` 复用或创建拼图 → 附已有转写 → 模型 → `:111` 保存摘要。

`VideoViewModel.cs:781` 远程关键帧已有磁盘缓存，未缓存下载并发上限为 4；逐帧按 ID 请求，必要时回退按原序号请求。视频摘要并不在此流程自动触发语音转写，只附带已存在的转写文本。

使用 SQLite `mode=ro`，没有通过应用构造器打开旧库，不触发 schema 迁移。该镜像仍为 schema92，有 8603 照片和 529 视频。

- 照片第一批 128 项有效描述判定：4.59ms。`EXPLAIN QUERY PLAN` 命中图片主键、描述的 image_id 索引及内容派生的 content_sha256/kind 复合索引。
- 另一轮照片采样只完成 17/68 页：单页中位 2.58ms，最大 5087.93ms，合计 21428.44ms。这 17 页没有匹配到当前有效描述；此结果说明判定查询的耗时分布，不是全库纯跳过时间。
- 529 视频的 5 页批量判定：匹配 448 个已有有效摘要，总计 2265.41ms；单页中位 446.29ms、最大 869.39ms。另一轮相近结果为总计 2273.31ms。

以上 SQL 抽样与运行中的媒体任务、开发构建并发，未控制冷暖缓存或磁盘负载。没有足够证据把长尾归结为具体锁、磁盘、杀毒软件或 SQL 计划问题；需隔离负载后复测。未完成的诊断已停止，只停止本次自有诊断，不影响 GUI/模型程序。

## 优先优化建议

### 1. 先补关联计时，区分响应头与完成

- `OpenAiCompatibleCloudVisionAnalyzer.cs:84` 使用 `ResponseHeadersRead`，`:85` 的“response received”仅表示响应头，`:87` 才读取完整正文。加入同一 requestId，并记录预处理、headersMs、bodyMs、总耗时和字节数；解析失败也保留安全阶段码。
- `MediaDescriptionBatch.cs:51` 已有条目秒表，目前耗时仅写在失败日志。成功和复用也应记录 runId/attemptId、媒体类型/数字 ID、耗时，区分真正推理完成与执行前复用。
- 将 GUI requestId 传到 IndexService，再传给 Agent；现在 `AgentConnectionRegistry.cs:369` 又生成自己的请求 ID，无法直接按同一 ID 跨端串联。
- 将视频“摘要状态”和“关键帧元数据”的两个 `Descriptions.VideoState` 拆为明确操作名，并记录帧数、缓存命中数、请求次数、下载、拼图、模型和保存耗时。
- `CloudVisionAnalysisService` / `VideoSummaryService` 的数据库委托使用带 operation 名称的 `UiWork.RunDatabaseAsync` 重载，才可区分等待共享数据库门与实际执行。目前部分调用没有名称或耗时日志。

日志只写数字 ID、次数、字节数、耗时和安全错误码，不能写人名、描述、GPS、原图路径或凭据。

### 2. 立即可做的低风险改进

- `DirectoryMediaDescriptionWindow.cs:246` 已持有 `VideoRecord item`，却调用 `MaterializeRemoteFramesAsync(..., item.Id)`；改为已有的 `(..., item, token)` 重载，可省掉 `VideoViewModel.cs:775` 的重复视频引用快照。现场每项大约省一次中位 53.5ms 的读取，但需保留后续内容有效性校验。
- `:234` 的摘要状态与关键帧元数据可在一个只读快照内获取；减少每视频独立连接/事务开销，同时保持读取一致。
- 只下载摘要真正使用的最多 12 个可用关键帧。不能简单在原列表上 `Take(12)`：原逻辑先剔除不可读帧再取前 12 个，简单截断会改变失败帧后的补位行为。建议物化方法增加 `maximumUsableFrames`，分批补足，并始终保留原始 ordinal 供回退端点使用。
- 重复检查发现结果之外的“执行前复用”必须保留；它可以防止同内容并发重复模型调用，不应作为冗余直接删除。

### 3. 处理主要耗时段

- 对已核验、已去元数据并符合尺寸上限的 JPEG，考虑在强类型的受信输入契约下复用编码结果，避免客户端再次解码/编码。不能仅凭路径或扩展名绕过清洗。
- 用已存在的媒体准备分段指标定位编码长尾；分别测无模型负载与模型并发时的解码/编码。不要直接把并发数从 2 提到 4，媒体通道和模型资源可能更加竞争。
- 针对本地模型，比较并发 1/2/4 的总吞吐、每项 p95、显存和 UI 响应；以吞吐和稳定性选值。当前 `MediaDescriptionBatch.cs:83` 总 worker 数为照片/视频并发的最大值，而非两者之和，共用队列也可能出现队首阻塞。拆分照片/视频有界队列可改善公平性，但总模型并发必须仍有上限。
- 长期可以让经授权的分析输入在来源 Agent/服务端直接交给模型，减少“分析图先下发 GUI，再随模型请求回传”的往返。需要保持来源指纹、独立云端授权、预算和结果持久化，不应绕过现有安全通道。

### 4. 为跳过路径单独验收

建立“全部已描述”和“少量新增/大量已有”两种固定样本，分别测冷/暖缓存、无后台负载/并发同步下的首个跳过反馈、全量扫描、SQL 页耗时、网络请求数和模型调用数。验收中明确后两者必须为零。对当前长尾先测磁盘和连接开销，再决定是否需要跨页复用快照或改 SQL；已经命中索引的查询不宜未经证据重写。

`Descriptions.SyncCounts` 是每 30 秒后台刷新，通常不在每项模型关键路径，但启动前及任务结束会等待它。将该状态刷新与首次发现解耦可改善启动反馈；慢读也应独立显示“同步状态刷新中”，避免用户误认为分类/描述仍未完成。

## 补充：照片采样未命中不等于全部描述失效

本补充仅核对代码、已有日志和上面的诊断结果，没有再执行生产数据库查询。

### 采样代表性与同步证据

前述 17 页照片抽样按 image ID 取前 2176 个引用，并非用户选定目录的 path 顺序，不是随机分层样本。没有匹配到有效描述，不能推出全库没有描述、镜像同步失败，或已有描述全部被判失效。

既有 GUI 日志在 16:21 至 18:26 多次记录 `Remote metadata applied` 的 `analyses=58`，18:33 为 `analyses=60`。这证明当时客户端确实接收到照片描述元数据，数量还在增长；不能仅凭这些计数证明本地/远程每个版本完全一致，也不能证明 58/60 条都落在这 2176 个抽样引用中。之前 8603 照片的全库审计仅有约 58 条照片描述，因此不能把视频描述的覆盖率套用到照片。

### 界面“有描述”与目录“有效描述”不是同一个条件

- `src/Picer.App/ViewModels/MainViewModel.cs:1306` 的图片信息读取 `CloudVisionRepository.GetLatestCompleted`。
- `src/Picer.Core/Vision/CloudVisionRepository.cs:195` 的该查询只要求 `status='completed'` 且 `result_json` 非空，随后取最新记录；没有校验该结果的源文件大小、修改时间与当前照片是否一致。
- 目录批量判定在 `CloudVisionRepository.Directory.cs:23` 附近，还要求非空摘要、源大小与修改时间匹配，或者存在满足内容复用条件的派生记录。

因此旧描述仍可显示，但目录认为当前文件需要重新描述。这可能是正确的内容版本失效，也可能是旧协议缺少身份字段：`PicerDatabase.cs:2507` 对新导入且缺失 `SourceFileSize/SourceModifiedUtc` 的描述使用 `0`/空串，界面仍能显示，目录则不能证明其有效。不能为提高跳过率直接删掉文件身份校验。界面宜显示“历史描述/当前文件待更新”，避免把旧显示结果等同于可复用结果。

目录首次跳过判定没有按当前 provider、模型或提示版本过滤；单项 `HasCurrentDescription` 也没有要求当前配置相同。因此“更换当前 provider 或模型”本身不能解释批量判定不命中。下游 `IsCurrent` 有更严格的模型/提示/位置指纹条件，但只有未在目录发现阶段跳过的项才会进入该路径。

### 已确定的契约缺口：等价时间文本可能过度失效

存在静态代码可确定的格式不一致风险，尚无生产样本证明它是此次未命中的原因：

1. `PicerDatabase.DescriptionAcceptance.cs:41` 起验证修改时间可以解析为 `DateTimeOffset`，`:61` 附近按 UTC 时刻比较，因此允许 `Z`、`+00:00` 等表达同一时刻的格式。
2. `PicerDatabase.cs:2508` 将 `analysis.SourceModifiedUtc` 原始文本写入描述投影，没有统一格式。
3. `CloudVisionRepository.Directory.cs:25`、`CloudVisionRepository.cs:95` 的跳过查询使用 TEXT 精确相等。

例如同一大小且 UTC 时刻相同的 `2026-10-29T01:02:03.0000000Z` 与 `2026-10-29T01:02:03.0000000+00:00`，会被接受为同一文件版本，却不能通过上述文本比较。在没有可救回结果的共享内容派生记录时，会错误地进入待描述。这是可触发的过度失效缺口，但不能据此声称当前 17 页就是该原因。

同类精确文本比较还出现在 `PicerDatabase.DescriptionSync.cs:21` 的历史未同步恢复筛选及 `:124` 的本地 outbox 投影保护，应统一审核，而非只修目录按钮。建议用统一、精确到原始时间精度的版本比较帮助函数，并补等价时区格式的隔离回归。不要直接用只保留秒/毫秒的 SQL 日期函数替代，以免把真实的细粒度修改误判为未变化；也不要随意改写同步载荷的时间文本，描述 version ID 和回执核对使用完整载荷摘要，格式规范化必须兼顾这些身份契约。

后续现场核实只需在资源空闲时对“界面确实显示、目录却未跳过”的少量指定引用比对：当前大小/修改时间、描述来源大小/时间、解析后 UTC 是否相同、共享派生是否存在、版本是否已回读。当前证据不足以断言是同步遗漏，仍不应重跑整库描述来验证。
